# 衰落与多径

2026-09-27。给引擎加上时变的链路:阴影衰落与小尺度衰落,默认关闭,按场景开启。

## 1. 为什么要做

现在链路损耗由 `buildLinkTable` 一次性预计算成静态表,只由几何与墙决定。
于是**同一个位置永远得到同一个电平**,后果比听上去大:

- 重传只可能来自碰撞,**永远不可能来自链路变差**
- `rate-fallback` 这门课教的降速机制,在这个引擎里**没有存在的理由**——
  没有任何东西会让一条链路时好时坏
- 速率控制的全部意义是应对变化的信道,而这里信道不变

也就是说课程里有一整块在教一个本仿真器演示不出来的现象。这与本仓库反复在抓的
"说的和跑的不一致"是同一类问题,只不过这次是**缺失**而不是**错误**。

## 2. 建什么,不建什么

**建**(两层,合起来就是链路电平随时间起伏):

| 层 | 模型 | 变化快慢 |
| --- | --- | --- |
| 阴影衰落(shadowing) | 对数正态,σ 可配 | 慢:在一个相干时间内不变 |
| 小尺度衰落(small-scale) | 瑞利(NLOS)或莱斯(LOS,K 因子可配) | 快:逐帧 |

**不建**,而且要在课程的 `limits` 里写明:

- **时延扩展与频率选择性衰落**。那需要子载波级建模,代价与本切片完全不同;
  本切片的衰落对整个信道带宽是平坦的(flat fading)。
- **多普勒与运动**。节点不动,相干时间是个配置值而不是从速度推出来的。
- **角度扩展与天线方向图**。

## 3. 最关键的一条:抽样必须与调用顺序无关

`linkDbm(txId, rxId)`(`src/engine/channel.ts:398`)是静态链路值的唯一咽喉,
也是衰落的插入点。但**它在一帧的生命周期里会被调用多次**——载波侦听一次、
捕获判定一次、信干噪比每次重算一次。若每次调用都从一个有状态的随机流里取下一个数:

- 同一帧在同一个接收机那里会得到**不同的电平**
- 结果依赖调用顺序,而调用顺序依赖事件队列的细节
- 确定性会以最难查的方式破掉:同样的场景同样的种子,换一个无关的改动就变了

**所以不用有状态的随机流,用确定性哈希抽样。** 一次抽样由
`(场景种子, 发端 id, 收端 id, 键)` 决定,函数纯、可重入、与顺序无关:

```
shadowDb(tx, rx, t)  = normal(hash(seed, tx, rx, 'shadow', floor(t / coherenceNs))) * sigmaDb
smallScaleDb(tx, rx, frameId) = fadeDb(hash(seed, tx, rx, 'fast', frameId))
```

- 阴影的键是**相干区间序号**,所以它在一个相干时间内恒定,跨区间才变。
- 小尺度的键是**帧标识**,所以它在一帧之内恒定,逐帧才变。

两者都是纯函数,同样的输入永远同样的输出。这条是本切片的验收核心,
测试要直接考它:同一帧反复查 100 次必须得到同一个值。

## 4. 配置

场景加一段,**整段可缺省**;缺省即今天的行为。

```ts
export interface FadingCfg {
  /** 对数正态阴影的标准差,dB。0 表示不加阴影。 */
  shadowSigmaDb: number
  /** 阴影的相干时间,ms:同一区间内阴影值不变。 */
  coherenceMs: number
  /** 小尺度衰落的分布。 */
  smallScale: 'none' | 'rayleigh' | 'rician'
  /** 莱斯 K 因子,dB;仅 smallScale 为 rician 时有意义。 */
  ricianKdB: number
}
```

默认值(**仅在用户显式打开时才生效**):`shadowSigmaDb: 4`、`coherenceMs: 100`、
`smallScale: 'rayleigh'`、`ricianKdB: 6`。四个都标 `model`——
室内实测的 σ 常落在 3–8 dB,K 因子常落在 3–10 dB,本仿真器各取一个中间值。

跨字段校验:`ricianKdB` 只在 `smallScale === 'rician'` 时接受,理由与既有那些
规则同一形状(一个不起作用的设置不该静静留在计划里)。

## 5. 硬约束:既有场景逐字节不变

`fading` 缺省时,`linkDbm` 必须返回**与今天完全相同的数**——不是"几乎相同",
是同一个浮点数。做法是缺省时根本不进衰落分支。

`tests/fixtures/lesson-hashes.json` 与 `uwb-record-hashes.json` 在本切片结束时
必须**零 diff**。这一条先于任何新 fixture 验证。

## 6. 验收:跑完整轮,读它的输出

这是上一轮花最大代价换来的纪律,写进本规格的验收标准:

1. **确定性**:同一场景同一种子跑两次,时间线哈希必须相同。衰落打开时也必须相同。
2. **顺序无关**:同一帧的同一条链路查 100 次,得到同一个值。
3. **真的起作用了**:打开衰落之后,跑一个静止场景,`RX_FAIL` 或 `RETRY` 的
   记录数必须 **> 0**;关闭时必须为 0(在一个几何上本来就不丢帧的场景里)。
   这一条是"功能真的接通了"的证据,算术测试替代不了。
4. **速率会变**:打开衰落之后,同一条链路在一次运行中选过**至少两个不同的 MCS**。
   这正是 `rate-fallback` 一直没有理由存在的那件事。

## 7. 课程

本切片**不写新课**,但要改两处既有内容,否则课程会立刻变成假话:

- M1 四课的 `limits` 里"没有衰落,也没有多径"要改成"默认没有;可以在场景里打开",
  并把"时延扩展与频率选择性不建模"作为新的一条补上。
- `rate-fallback`、`rate`、`rate-cost` 三课的 `limits`(它们还在 `NOT_YET` 清单上)
  由后续的铺开波次写,届时它们终于有真话可说。

新课等铺开波次之后单独一刀,那时可以按"为什么需要速率控制"来组织。

## 8. 明确不做

- 不改 `buildLinkTable`。它是几何与墙那一层,按设计就是静态的,衰落叠在它之上。
- 不给 UWB 侧加衰落。UWB 有自己的信道模型与自己的课程,混在一起会让两边都难验。
  本切片只动 Wi-Fi 侧,并在规格里说明这是范围决定而非遗漏。
