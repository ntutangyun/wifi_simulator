# W3：多对多测距按 IEEE 802.15.4-2024 §10.32.6／§10.32.7 改正（2026-11-11）

审计表 `docs/uwb-standard-audit.md` 第 2 项。建在 W2b（`2a152e6`：应答方从 RDM 读时隙、块由整数个轮组成）之上。
硬规则照旧：只用标准定义的帧、信息单元与规则；下面每一项都对照语料库原文（`ieee_standards/text/802154-2024.json`，第 486–490、451–455、493–495、500–501、528–529 页）核过。

## 1. 以前与现在

以前：多对多一轮没有控制消息，场景里每台 UWB 设备都是「参与者」，按 id 依次各发一帧，帧里带自己的发送时刻（TXT IE）与此前收到的每一帧的到达时刻（RXT IE）——这两个信息单元 802.15.4-2024 没有定义；每一对距离由排在前面的那台算。N 帧（双边 2N）得 N(N−1)/2 对。

现在：标准的一轮。

## 2. 未实现（schema 拒绝，② 标「未实现」）

- 竞争式多对多（§10.32.6 允许两个阶段都竞争）。
- 测距结果上报：§10.32.6 说响应方可以请求测距结果，由发起方再发数据帧；§10.29.8.3 说双边时发起方可以请求 TOF。本仿真器两种形态都不上报，距离留在算出它的设备处（图 10-240、10-241 本身也没有请求）。
- 多对多的延后形态、固定回复时间形态（`replyTime` 只能是 embedded）。
- 多对多下的 SP3、RMNR、辅助信息交换、到达角。
- 控制器不是发起方（图 10-222 一般情形）。
- `rcmValidityRounds` 只能是 1：多对多每块一轮，RCM 的有效轮数不能超过块里剩余的轮数（§10.32.9.1）。

## 3. 本仿真器的取值与取法（标准留给上层的）

- 控制器是按 id 排在最前的发起方（§10.32.9.1 只说一个会话一个控制器）。
- 时隙顺序：启动阶段按发起方 id、应答阶段按响应方 id 依次排开；双边最终帧接在应答之后，按启动顺序。RDM 每台设备一个元素、一个时隙（§10.32.9.8「the number of slots assigned by the RDM IE」），最终帧的时隙由这条顺序推出——标准没有说双边多对多的最终帧时隙怎样分配。
- 一个 RRTI IE 列出全部发起方（元素都带地址）。§10.32.6 正文说「insert an RRTI IE ... for each initiator」、图 10-240 写「RRTI IEs」；图 10-208 的列表格式允许一个 IE 列多个回复时延，W2（审计 #8）在一对多 Final 上也采用一个 IE。两种读法字节数不同（一个 IE：3 + 6M；每个发起方一个 IE：9M）。
- RRMC 的字段取值（Ranging Control Information 0/1/2/3、Reply Time Request 等）不逐位进帧描述，只按 3 字节计长度。

## 4. 核查不了的

- 「insert an RRTI IE for each initiator」是一个 IE 列多个元素还是每个发起方一个 IE，见上。
- 双边形态里发起方的 RRMC (2) 是否同时置 Reply Time Request：图 10-241 只写「RRMC IE (2)」，本仿真器的启动消息不建字段。
- 单边形态的应答是否还应带 RRMC：图 10-240 没有，一对多的图 10-235 有（RRMC (1)）；照图 10-240 不带。
