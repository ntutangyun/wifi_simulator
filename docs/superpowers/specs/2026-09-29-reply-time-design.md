# 五种测距形态：回复时间放在哪里

2026-09-29。已发布标准 §10.29.6 列了五种测距过程，本仿真器建了两种。这一刀补齐
另外三种。

## 1. 为什么这是最大的一块空洞

`docs/uwb-feature-coverage.md` 把它们排在一起，看得很清楚：

| 形态 | 条号 | 现状 |
| --- | --- | --- |
| SS-TWR 回复时间**延后** | §10.29.6.3 | 未建模 |
| SS-TWR 回复时间**嵌入** | §10.29.6.4 | 已建模 |
| SS-TWR **固定**回复时间 | §10.29.6.5 | 只长在 4ab 的 MMS 路径上 |
| DS-TWR 时间信息**延后** | §10.29.6.6 | 未建模 |
| DS-TWR 时间信息**嵌入** | §10.29.6.7 | 已建模 |

这五种测的是同一个距离，用的是同一套算术（`ranging.ts` 一行都不用改）。
不同的只有一件事：**那几个时间量，从产生它的设备走到需要它的设备，走的是哪条路。**

所以它不是五个功能，是一张取舍表——而且表里每一格都能在仿真里量出来：帧长、
轮长、谁最后手里有距离。课程现在讲测距只讲一种走法，学生会以为那是唯一的走法。

## 2. 真正的那条约束：你不能把一个数放进它自己测量的那一帧

SS-TWR 的回复时间 `Treply = T3 − T2`：响应方收到 Poll 的时刻到它自己发出
Response 的时刻。**T3 是这一帧自己的发送时刻。** 要把 `Treply` 写进这一帧的
载荷，响应方必须在还没发之前就知道自己会在什么时候发。

这就是三种形态存在的全部理由：

- **嵌入**（§10.29.6.4）：硬件能预约发送时刻，于是 T3 提前已知，写进 RRTI IE。
  本仿真器今天走这一条。
- **延后**（§10.29.6.3）：硬件做不到，于是 Response 先发出去、发完了再回头读自己的
  发送时间戳，放进**后面一条报文**里。多花一个时隙，换掉对硬件的要求。
- **固定**（§10.29.6.5）：双方事先约定一个 `Treply`，响应方**在收到之后的固定时延处**
  发送，这个数根本不上空口。帧最短，但它把要求转移了：响应方必须真的踩准那个时刻。

DS-TWR 的两种是同一个问题的另一半：Final 要不要携带 `tround1/treply2`。

## 3. 配置

`UwbSessionCfg` 加一个字段：

```ts
/** 回复时间/时间信息走哪条路（标准 §10.29.6.3–.7）。缺省 'embedded' 是今天的行为。 */
replyTime: 'embedded' | 'deferred' | 'fixed'
/** 'fixed' 专用：第一个响应方的固定回复时间，RSTU。响应方 k 的是这个数加 k 个时隙。 */
fixedReplyRstu: number
```

`replyTime` 默认 `'embedded'`，`fixedReplyRstu` 有默认值，所以**每个既有场景逐字节
不变**——两份 fixture 零 diff 是这一刀先于一切的验收条件。

### 3.1 schema 必须拒绝的组合

- **`ds` + `fixed`**：标准枚举的五种里没有这一种。DS-TWR 只有延后与嵌入两种
  时间信息形态。拒绝的理由要写在消息里，不是"暂不支持"。
- **`contention` + `deferred`**：竞争轮里响应方是**抽**到时隙的，它的延后报文没有
  一个固定的时隙可去。这和已有的"竞争轮不支持 DS-TWR"是同一条理由的同一个后果。
- `contention` + `fixed` **允许**，而且是最该允许的一格：竞争轮里帧越短越好。

## 4. 五种形态的轮形

`uwbSlotsPerTag` 多一个维度：

| 形态 | 时隙数 | 轮的构成 |
| --- | --- | --- |
| SS 嵌入 | A+1 | Poll \| A 个 Response（带 RRTI） |
| SS 固定 | A+1 | Poll \| A 个 Response（不带 RRTI） |
| SS **延后** | **2A+1** | Poll \| A 个 Response（不带 RRTI）\| **A 个延后报文** |
| DS 嵌入 | 2A+2 | Poll \| A 个 Response \| Final（带每锚点的时间）\| A 个报告 |
| DS **延后** | 2A+2 | Poll \| A 个 Response \| **Final（空的）** \| A 个报告 |

DS 延后的时隙数没变，变的是**载荷搬了家**：Final 从 14+12A 字节变成恒定 14 字节，
锚点侧的时间照旧在报告里。

## 5. 帧长，以及它买到的那个上限

| 帧 | 嵌入 | 延后 | 固定 |
| --- | --- | --- | --- |
| SS Response | 20 | 14 | 14 |
| SS 延后报文 | — | 17（MHR+RRTI+FCS） | — |
| DS Final | 14 + 12A | 14 | — |

**`UWB_MAX_ANCHORS = 9` 是从嵌入式 DS Final 推出来的**，注释就写着"Final 每多一个
锚点长 12 字节，9 个是 122 字节，10 个是 134，超过 PHR 能表达的 127 字节 PSDU"。

于是这一刀有一个可以量出来的后果：**延后的 Final 不长，那个上限就不该是 9。**
延后之后轮里最长的帧变成 Poll（27+3A），上限落在 33。

同一件事还暴露了一个既有的不准确：**SS-TWR 今天也被卡在 9**，而 SS 轮里根本没有
Final。这个常数必须变成一个函数：`uwbMaxAnchors(method, replyTime)`，由轮里最长的
那一帧算出来，不是一个数。

**不要**直接把 33 写进代码。写成"轮里最长的帧 ≤ 127"这条约束，让上限被算出来，
并在测试里把五种形态的上限都钉住。

## 6. 固定回复时间：唯一一种不对齐时隙的发送

这是本刀最需要小心的一处。

如果响应方在**自己的时隙边界**发送，那么
`Treply = 时隙起点 − Poll 到达时刻`，**它随距离变化**。标签不被告知就算不出来。
所以"固定回复时间"在物理上必须意味着另一件事：

> 响应方在**它自己收到 Poll 的时刻之后的固定时延处**发送。

响应方 k 的固定时延是 `fixedReplyRstu + k × slotRstu`：会话只说第一个数，
排定表把其余的错开。标签从 Poll 的 RDM IE 知道 k、从会话配置知道那个数，
于是它能重建每个响应方的 `Treply`，而这个数一个字节都没上空口。

**后果，而且必须测出来**：Response 的发送时刻不再对齐时隙，它随距离漂
——离得远的锚点在绝对时间上答得晚，漂的量是 `2 × 飞行时间`。于是时隙够不够长
多了一条约束：

```
fixedReplyNs + Response 空口时间 + 2 × 最远飞行时间 + 守卫 ≤ slotNs
```

时隙不够长的时候会发生什么，本身就是那一课要教的东西：Response 越过时隙边界，
接收窗口已经关了，整轮以 `UWB_TIMEOUT` 收场——而 Poll 明明收到了。

这一条要有一个专门的测试：把 `fixedReplyRstu` 调到刚好越界，断言测距失败；
调回来，断言测距成功。**不是断言算术，是跑完整轮读输出。**

## 7. 谁最后手里有距离

这张表是 DS 延后真正的代价，而且它是课程里最值得读的一格：

| 形态 | 标签得到距离 | 锚点得到距离 |
| --- | --- | --- |
| SS 嵌入 | ✓ 收到 Response 时 | ✗ |
| SS 固定 | ✓ 收到 Response 时 | ✗ |
| SS 延后 | ✓ 收到延后报文时 | ✗ |
| DS 嵌入 | ✓ 收到报告时 | ✓ **收到 Final 时** |
| DS 延后 | ✓ 收到报告时 | ✗ |

DS 嵌入是五种里**唯一**两端都拿到距离的：Final 把标签的两个时间带给了锚点。
把它延后，锚点就只是一个应答器了。

## 8. 算术不动

`src/uwb/ranging.ts` 一行都不改。`ssTwrRaw`、`ssTwrCorrected`、`dsTwr` 收的是
四个时间量，不关心它们是从哪一帧来的。**如果实现过程中发现要改它，那是搬运路线
建错了，回去看 §2。**

时钟偏移修正照旧对固定回复时间生效：那个"固定"时延是按**响应方自己的晶振**数的，
所以 `ssTwrCorrected` 的 `(1 − coffs)` 一项该乘的还是它。

## 9. 验收：跑完整轮，读它的输出

1. **五种形态量出同一个距离。** 同一个场景、同一个种子，五种 `replyTime`/`method`
   组合各跑一轮，读 `UWB_RANGE` 记录：五个距离在时间戳噪声之内一致。
   这是整刀的验收——五条不同的搬运路线，一个物理距离。
2. **帧长按 §5 的表变。** 读时间线里的帧描述，不是读源码里的常数。
3. **上限按 §5 移动。** 五种形态各问一次 `uwbMaxAnchors`，并且让 schema 在超限时
   拒绝、在限内接受。
4. **锚点侧的距离只在 DS 嵌入出现**（§7 的表）。读记录的 `node` 字段。
5. **固定回复时间的时隙边界**（§6）：越界失败，回退成功。
6. **两份 fixture 零 diff**，`replyTime` 缺省时。

## 10. 明确不做

- **§10.29.6.2 的控制面。** 结果传输这一刀补齐了，但"用什么报文启停或重配一个
  会话"仍然没有：这个仿真器没有一个 MAC 原语，`replyTime` 是场景配置而不是空口
  协商的结果。这条要写进两课的 `limits`。
- **RRTN IE。** 两端不商量回复时间，它是配置好的。同上。
- **响应方踩不准固定时刻。** 本仿真器的响应方总是精确命中 `rxPoll + fixed`，
  真实设备有发送时刻抖动。抖动会直接变成距离误差（`Treply` 错 1 ns ≈ 15 cm），
  这是固定形态真实的弱点，而本刀不建模它。`limits`，标 `unmodelled`。
