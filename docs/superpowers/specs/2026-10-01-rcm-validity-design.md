# 一条控制消息管好几轮，以及没收到的那一方怎么说话

2026-10-01。已发布标准的 ARC IE「RCM Validity Rounds」字段（§10.32.9.1）与
§10.34 的测距消息未收到交互（RMNR IE）。`docs/uwb-modellable-backlog.md` 的切片 3
前半。

## 1. 先说清一件事：这两个特性必须一起做

原来的排期把 §10.34 当成一个独立的「出错时会发生什么」来做。**读完正文发现那样做不出来。**

§10.34 的场景是这样的：一个响应方**收到了控制消息（RCM）**，但**没收到本轮的测距
启动消息**。它不在自己的时隙里干坐着，而是发一帧带 RMNR IE，说「我没收到」——
而发这一帧同时隐含确认了「你的控制消息我收到了」。

问题在于：**本仿真器的 Poll 把这两件事合成了一帧。** 它既带控制内容
（ARC + RDM + RRMC），又是被打时间戳的那一次启动。于是「收到了控制消息、
没收到启动消息」这个状态在引擎里**根本不存在**——Poll 丢了就是两样都丢了，
而一个连 Poll 都没收到的响应方**连自己该在哪个时隙发言都不知道**，它发不出 RMNR。

所以 RMNR 不是单独一个特性，它**要求控制消息的有效期跨越多轮**。标准正是这么写的：
ARC IE 的 **RCM Validity Rounds** 字段（§10.32.9.1，Content Control 的 bit 9–14，
6 位，所以 0–63 轮）规定「本轮以及 RCM 之后若干轮」共用这一条 RCM。
后面那几轮里没有 RCM，只有启动消息——**这才是 RMNR 有话可说的那个状态。**

**这一条是本刀的骨架，也是那一课的骨架：一个机制的前提条件，比机制本身更值得教。**

## 2. RCM 有效轮次：买到的是空口时间

会话加一个字段 `rcmValidityRounds`，1 到 64（标准的 6 位字段表示 0–63，
本仿真器按「这一条 RCM 管几轮」计数，所以 1 表示今天的行为：每轮一条 RCM）。

一个块里的轮次因此分成两种：

| 轮次 | 发什么 | 帧长（A 个锚点） |
| --- | --- | --- |
| 每 R 轮的**第一轮** | RCM + 启动：ARC + RDM + RRMC，就是今天的 Poll | 27 + 3A |
| 其余 R−1 轮 | **只有启动消息**：没有 ARC，没有 RDM | 14 |

省下的是 `13 + 3A` 个字节，每 R 轮省 R−1 次。四个锚点、R = 4 时：每块省 75 个字节
的空口时间，而测距结果一个数都不变。**这是本刀的验收数之一，要跑出来。**

**缺省 `rcmValidityRounds = 1`**，所以既有场景逐字节不变。

### 2.1 启动消息里还必须留下什么

少了 RDM，响应方怎么知道自己的时隙？**它从上一条 RCM 知道**——这正是「有效期」的
含义：那张时隙表在 R 轮里一直有效。所以启动消息不需要重发它。

但启动消息仍然要能被认出属于**哪一条 RCM 管的哪一轮**，否则一个刚上电的设备会把它
当成一条自己没有配置的轮次。引擎里块号与轮号已经在每一帧上（`UwbInfo` 的
`block`/`round`），够了——**不要为此发明新字段**。

## 3. RMNR：一个零内容的 IE，携带两条信息

RMNR IE（§10.34.2.1）**没有 Content 字段**，正文写得很直接：
"This IE is formatted without any Content field."
所以它就是一个 IE 头部，本引擎里 `UWB_IE_HDR_BYTES` = 2 个字节。

而它携带的信息有两条，全靠「它出现在哪、什么时候出现」：

| 信息 | 从哪读出来 |
| --- | --- |
| 是谁在说话 | 它发在哪个时隙——而时隙表来自那条仍然有效的 RCM |
| 「你的控制消息我收到了」 | 它**发出来了**这件事本身（正文：implicitly confirm its receipt of the RCM） |
| 「本轮的启动消息我没收到」 | 它发的是 RMNR，而不是一条带时间的响应 |

**这是这一课最值得读的地方：一个零字节内容的信息单元不是一条空消息。** 信息不在
载荷里，在「谁、在哪、本该发什么却发了这个」里。

### 3.1 引擎里它取代的是「沉默」

今天的响应方在没收到 Poll 时什么都不做，整轮留下一条 `UWB_TIMEOUT`，而发起方
**无法区分**三件事：这个锚点没听到、这个锚点听到了但回答丢了、这个锚点不在了。

RMNR 把第一种从另外两种里分出来。所以验收要测的是**发起方在一轮结束时知道多少**，
不是「RMNR 发出去了吗」。

## 4. 配置

```ts
/** 一条 RCM 管几轮（标准 §10.32.9.1 的 ARC IE，RCM Validity Rounds，6 位字段）。
 *  1 表示每轮一条 RCM，也就是今天的行为。 */
rcmValidityRounds: number   // 1…64，缺省 1
/** 响应方在持有有效 RCM、却没收到本轮启动消息时，是否发 RMNR（标准 §10.34）。
 *  缺省 false。 */
rmnr: boolean
```

**`rmnr` 为 true 而 `rcmValidityRounds` 为 1 时 schema 必须拒绝**，理由就是 §1：
那个状态在这种配置下不存在，没收到 Poll 的响应方连自己的时隙都不知道。
消息里要把这条因果说出来，这是本刀唯一一条「拒绝是为了讲清一个道理」的规则。

## 5. 不做，以及为什么

- **§10.35 的辅助信息交换与 §10.36 的多消息收妥确认**：排在切片 3b。
  两者机理已经读通（RAICT IE 的 Request/Frames Remaining，RMMRC IE 的
  按发起方分列的收妥位图，以及 ARC IE bit 15 的 MMRCR 请求位），不是举证问题，
  是切片大小问题。§10.36 的正文图示用的正是**多对多**，所以它接在切片 2 之后最顺。
- **ARC IE 的其余控制位** 仍然只建长度不建布局。但这一刀之后覆盖表可以说得更准：
  Multi-node Mode 的取值 2 就是切片 2 建的那个多对多，Ranging Round Usage 的
  取值 3 选的是 §10.35。
- **MCPS 原语** 照旧不建：本仿真器没有一个 MAC 原语，`rcmValidityRounds` 是场景
  配置而不是空口协商的结果。

## 6. 验收：跑完整轮，读它的输出

1. **省下的空口时间。** 同一场景，`rcmValidityRounds` 1 与 4 各跑一块，
   读时间线里每一帧的字节数：第一轮 27 + 3A，其余三轮 14，每块省 `3 × (13 + 3A)`。
   **而 `UWB_RANGE` 的距离逐字段相同**——省掉的是控制开销，不是测量。
2. **RMNR 把「没听到」从「别的原因」里分出来。** 一台锚点移到墙后，跑一块：
   关掉 `rmnr` 时发起方只拿到 `UWB_TIMEOUT`；打开时它收到那一帧，
   记录里要能看出「这个锚点仍然持有 RCM，但本轮没收到启动消息」。
3. **RMNR 帧长是 MHR + 2 + FCS**，并且 `ies` 恰为 `['RMNR']`。
4. **拒绝规则**（§4）：`rmnr` 为 true 而 `rcmValidityRounds` 为 1 时被拒。
5. **第一轮之外的轮次没有 RDM**：读帧的 `ies`，后续轮次的启动消息里没有它。
6. **既有场景逐字节不变**，两份 fixture 零 diff。
