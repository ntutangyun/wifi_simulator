2026-10-05。基线提交 `70fc934`（切片 4a + 4b 全量 249 文件 / 6562 条绿）。
已发布标准 IEEE Std 802.11-2024（§19.3.5、§19.3.20、§19.5 Table 19-27、Table 19-6、
§21.3.6 Table 21-5、§26.7.5、§27.1.1、§27.2 Table 27-1、§27.3.9 Table 27-13、§27.3.23、
§27.5 Table 27-86、§32.3.13、§10.3.2.9、§10.6、§17.4.3）与 IEEE Std 802.11be-2024

§36.3.22、§36.5.6 Table 36-76）。

**这份规格的结论是：建，按 4a §7.1 的立意建，但不按它说的那个做法建；
而「长保护间隔在这个引擎里买不到任何东西」这件事不是绕开的难点，是这一课的正文。**

三句话说完为什么这不是耍读者：

1. **代价这一侧是精确的，而且不止一个数。** 逐 PPDU 量出来：双倍保护间隔
   **+1.22 % ～ +5.82 %**（中位 4.70 %），四倍 **+3.66 % ～ +17.47 %**（中位 14.09 %）——
   **同一个旋钮，代价跨一个数量级，而决定它的是这一帧有几个符号。** 这件事今天的课程里没有。
2. **收益这一侧的缺席是标准的形状，不是我们的省略。** `delay spread` 这个词在 802.11-2024
   的 5956 页里只出现 **3 页**、802.11be-2024 的 1020 页里只出现 **1 页**，而这四处是**同一句话**：
   GI 插在每个数据 OFDM 符号前，用途是对抗时延扩展（§19.3.20 / §27.3.23 / §32.3.13 /
   be §36.3.22）。**标准说了 GI 买什么，却从不给那样东西一个数。** 4a 为 σ_τ 做的穷举检索
   （4a §1.4）我复核过，结论不变。
3. **所以这一刀能做的、也只能做的，是把一侧算准、把另一侧的空缺指名道姓地钉住。**
   §5 的「允许但空转」里有**两条是量出来的、而且是这一刀自己造的**，
   §2.2 第三组数更要紧：**在真实的一轮里，掉帧率会往两个方向都动，而两边都是重采样噪声。**
   不把这件事钉死，这一课会在第一次被人「验证」时给出一个假的收益。

§0 是更正，§1 是查证，§2 是那个必须正面回答的问题，§3 建什么，§4 fixture，
§5 允许但空转，§6 明确不做，§7 课程落点，§8 验收，§9 判断。

### 0.3 已发布课文里那条 `limits` 的数，和 4a 犯的是同一个错

`src/course/tier1/frame-anatomy-bytes.ts:122` 原话（节选）：

> 「真实设备会按信道的时延扩展在 0.8、1.6、3.2 µs 之间切换，**长保护间隔会让同样的字节

| GI | 这一帧 | 相对 57.6 µs |
| --- | --- | --- |
| 0.8 µs | 44 + 1 × 13.6 = **57.6 µs** | — |
| 1.6 µs | 44 + 1 × 14.4 = **58.4 µs** | **+1.39 %** |
| 3.2 µs（不算 4× LTF） | 44 + 1 × 16 = **60.0 µs** | **+4.17 %** |
| 3.2 µs（算 4× LTF） | 52.8 + 1 × 16 = **68.8 µs** | **+19.44 %** |

### 0.4 一条 brief 与 4a 都没有的事实：标准自己按保护间隔发布三列速率

这一条决定了 brief 的「技术决定二」（`mbps` 怎么办），所以单列。

802.11be-2024 **Table 36-76（EHT-MCSs for 242-tone RU, N_SS,u = 1）** 与
802.11-2024 **Table 27-86（HE-MCSs for 242-tone RU, N_SS = 1）** 的速率栏不是一列，
**是三列**：`0.8 µs GI | 1.6 µs GI | 3.2 µs GI`，取一位小数。
而 242 音调资源单元就是 20 MHz、单流——**正是 `PHY_MODES.he/eht` 那一列**。

量具：**仪器 C**。把 Table 36-76 的 14 行从语料里抄进探针，
对每一行算 `N_DBPS / (T_SYM / 1000)` 再取一位小数：

- **14 行 × 3 列，零处不符。**
- **`PHY_MODES.eht.mbps` 与 Table 36-76 的 0.8 µs 栏逐项相等**（14/14）。
- **`PHY_MODES.he.mbps` 与同一栏的前 12 项逐项相等**（12/12）。

而 `Math.round(x * 10) / 10` 这个取整约定也不是本仓库发明的：
§19.5 对 Table 19-27 逐字写明「data rates for a 400 ns GI are rounded to 1 decimal place」。

**所以 `mbps` 不是一个「要不要从 `symNs` 现算」的问题。它是一张查得到的三列表，
而今天的仓库存的是第一列、并且没有任何地方写明它是第一列。** 见 §3.6。

## 1. 机理与取值（查出来的，带条号）

### 1.1 三个取值、三个符号时长，全在一张表里 · `standard §27.3.9 Table 27-13` / `standard be §36.3.10 Table 36-18`

两张表逐字一致（HE 的在 802.11-2024 §27.3.9，EHT 的在 802.11be-2024 §36.3.10）：

| 参数 | 值 | 表里的说明 |
| --- | --- | --- |
| T_DFT,HE / T_DFT,EHT | **12.8 µs** | 数据字段的 IDFT/DFT 周期 |
| T_GI1,Data | **0.8 µs** | 基本（base）保护间隔 |
| T_GI2,Data | **1.6 µs** | 双倍（double）保护间隔 |
| T_GI4,Data | **3.2 µs** | 四倍（quadruple）保护间隔 |
| T_SYM1 | **13.6 µs** = T_DFT + T_GI1 = 1.0625 × T_DFT | 基本 GI 下的符号时长 |
| T_SYM2 | **14.4 µs** = T_DFT + T_GI2 = 1.125 × T_DFT | 双倍 GI 下的符号时长 |
| T_SYM4 | **16 µs** = T_DFT + T_GI4 = 1.25 × T_DFT | 四倍 GI 下的符号时长 |
| T_SYM | T_SYM1 / T_SYM2 / T_SYM4，取决于数据字段用的 GI | |

**于是 `PHY_MODES.he.symNs = 13_600` 不是一个代表值，它是 T_SYM1，有表、有和式。**
今天 `phy.ts` 的注释没有这么说（它把 13.6 µs 和 44/48 µs 的前导码并列成
「representative SU values」——**前导码是代表值，而 13.6 不是**）。这一句要补进 §3.1。

两张表还各有一条顺带有用的：T_GI,Pre-HE / T_GI,Pre-EHT = **0.8 µs**（前导码里传统字段的 GI，
L-LTF 那一个是 1.6 µs），**与数据字段的 GI 无关**。所以这一刀改的只有数据字段那一段。

### 1.2 `GI_TYPE` 是一个 TXVECTOR 参数，枚举值恰好三个 · `standard §27.2 Table 27-1` / `standard be §36.2 Table 36-1`

Table 27-1 的 `GI_TYPE` 行（`FORMAT` 为 `HE_SU`/`HE_MU`/`HE_ER_SU`/`HE_TB` 时在场）：
枚举类型，**`0u8s_GI` / `1u6s_GI` / `3u2s_GI`**，分别指 0.8 / 1.6 / 3.2 µs，
作用对象是 **HE-LTF 与数据字段**；表里那条 NOTE 说前导码里 pre-HE 字段的 GI 固定 0.8 µs。
Table 36-1 的同名行逐字对应（`FORMAT` 为 `EHT_MU`/`EHT_TB`）。

**所以「保护间隔是一个发送侧的选择」这件事是标准自己的措辞，而不是本仓库的建模决定。**
这也是 4a §7.1 立案时最站得住的那半句。

### 1.3 标准说了 GI 买什么——而全书只说了四次，一个数都没给

§19.3.20 / §27.3.23 / §32.3.13 / be §36.3.22 四处发送过程各有一句：
GI 按 TXVECTOR 的 `GI_TYPE` 插在**每一个数据 OFDM 符号**之前，
用途是 **对抗时延扩展（countermeasure against delay spread）**。

我按出现位置复核了 4a §1.4 的检索：`delay spread` 在 802.11-2024 里命中 **3 页**
（3482 / 4342 / 4831）、在 802.11be-2024 里命中 **1 页**（879），**四页就是上面四句**。
`coherence bandwidth`、`power delay profile`、`rms delay`、`tapped delay`、
`frequency selectiv`、`Rayleigh`、`Rician` 在两份文件里**全零**（4a 已查，我复核结论一致）。

**这就是这一刀的全部困难，而且它是标准的形状：
标准把 GI 的代价发布成三张表（Table 27-13/36-18 的符号时长、Table 27-86/36-76 的三列速率、
Table 36-26 的逐字段 GI），把 GI 的收益发布成一个没有数的名词。**

### 1.4 保护间隔与 LTF 类型是绑在一起的，而那一绑会动前导码 · `standard §27.1.1`、`§26.7.5` / `standard be §36.1.1`、`§35.7.5`

§27.1.1 与 be §36.1.1 各有一句同形的：该 PHY 支持 **0.8 / 1.6 / 3.2 µs** 三种 GI，
以及 **3.2 µs（1×）/ 6.4 µs（2×）/ 12.8 µs（4×）** 三种 LTF 符号时长（不含 GI）。
而两处的强制支持清单与 §26.7.5 / §35.7.5 的探测 NDP 规则把两者**配成对**：

| LTF | 允许配的 GI |
| --- | --- |
| 2× （6.4 µs） | 0.8 µs 或 1.6 µs |
| 4× （12.8 µs） | 3.2 µs |

**于是选四倍 GI 的同时就换了 4× LTF，而一个 LTF 符号从 6.4 + 0.8 = 7.2 µs
变成 12.8 + 3.2 = 16 µs——前导码多 8.8 µs。**

这个 8.8 µs 不是推测出来的，它还和引擎今天的两个前导码常数对得上：
HE SU 前导码按 Table 27-13 逐段加起来是 8（L-STF）+ 8（L-LTF）+ 4（L-SIG）+ 4（RL-SIG）
+ 8（HE-SIG-A）+ 4（HE-STF，非 TB）+ 7.2（1 个 2× HE-LTF）= **43.2 µs**，
引擎存的是 44 µs；EHT 把 HE-SIG-A 换成 U-SIG 8 + EHT-SIG 4 得 **47.2 µs**，引擎存 48 µs。
**所以引擎今天那两个前导码常数就是「2× LTF + 基本 GI」那一档**——
这件事今天没有写在任何地方，而它是 §3.2 能把 8.8 µs 加上去的依据。

### 1.5 三个 GI 都是强制的，而「基本 GI」对上行触发式 PPDU **不是** · `standard §27.1.1` / `standard be §36.1.1`

逐条读过两份强制支持清单（HE 的在 §27.1.1，分 STA / AP / non-AP STA 三段；
EHT 的在 §36.1.1），把 GI 相关的条目摘出来：

| PPDU 格式 | 强制的 (LTF, GI) 组合 | 0.8 µs 在不在里面 |
| --- | --- | --- |
| HE SU / HE ER SU | (2×, 0.8)、(2×, 1.6)、(4×, 3.2) | **在** |
| HE MU（AP 发 / non-AP 收） | (2×, 0.8)、(2×, 1.6)、(4×, 3.2) | **在** |
| HE TB（non-AP 发 / AP 收） | (2×, 1.6)、(4×, 3.2) | **不在** |
| EHT MU | (2×, 0.8)、(2×, 1.6)、(4×, 3.2) | **在** |
| EHT TB | (1×, 1.6)、(2×, 1.6)、(4×, 3.2) | **不在** |

（(4×, 0.8) 在两代里都是条件性的，HE 侧挂在 ER SU 的支持上，
EHT 侧是一个能力位 `dot11EHT4xEHTLTFand0point8usecGIImplemented`，缺省 false。）

**两条后果，都要用。**

1. **引擎今天的上行触发式 PPDU 跑在 0.8 µs 上，而那个组合对 TB PPDU 不是强制的。**
   这不违规（能力位允许），但它是一条该写进 `ofdma-ul` 的 `limits` 的事实。
2. **这一刀的场景小节只开放 1.6 与 3.2（§3.3），而那两个恰好是 TB PPDU 那一行的强制集。**
   拒绝基本 GI 的第一条理由是「写出来什么也不改」（§5），
   **而第二条理由是标准的：它是唯一一个对某个 PPDU 格式不强制的那一档。**

## 2. 这一刀真正的难点：买不到的那一半

### 2.1 收益为零不是「还没建」，是结构性的零，而且一行代码就能看出来

解调判决那条路上没有任何一个量带时间维度：

```
resolveLock → decodeThreshDb(frame, rid, r)            channel.ts:501-517
            → reqSinrDb(mode, mcs)                      phy.ts:275-277
            → PHY_MODES[mode].sensDbm[mcs] - noiseDbm(20, 10)
```

`decodeThreshDb` 的三个入参是 `frame`、接收端 id、接收端状态；它分流到
AMP 的三条常数、MU 成员那一份的 `reqSinrDb(mode, part.mcs)`、单用户的
`reqSinrDb(frame.mode, frame.mcs)`、或 `sinrThreshDb(frame.mbps)`。
**四条出口里没有一条读符号时长、也没有一条读任何时延量。**

量具：`reqSinrDb` 对 `he`/`eht` 的全部 MCS 各算一次，把 `PHY_MODES[*].symNs`
从 13 600 改成 16 000 再算一次 —— **两组逐项相同（26 个值，零差异）**。
这不是「目前相同」，是签名里就没有那个参数。

**所以在这个引擎里，长保护间隔花掉空口时间，而解调门限一分贝都不动。**

### 2.2 跑出来的三组数

三个量具，这份规格里每一个数都标到其中之一。

- **仪器 A（纯算术重定价）**：全部 81 课各跑自己的场景 `runUntil(150 ms)`（默认种子、
  只跑 `scenario()` 不跑 `variants`），取每一条 `TX_START` 里 `frame.mode ∈ {he, eht}`
  且非 AMP / 非 UWB 的 PPDU，**按 Table 27-13 的三个符号时长重新算它的空口时间**。
  不重跑，所以没有重采样。**9463 条 PPDU，落在 36 课上**（其余 45 课的场景里
  一条 HE/EHT PPDU 都没有）。

  > **读过它的实现了（2026-10-05 第三轮），不是推断。** 它跑的是**未经修改的引擎**、
  > 而且只跑基本档那一轮——场景里没有 `guardInterval` 一节，也不改 `PHY_MODES` 的任何字段。
  > 读完那一轮之后，它对每条 PPDU 做的是纯本地算术：
  > `head = PHY_MODES[mode].preambleNs + (muParts ? muExtraPreambleNs : 0)`，
  > `nsym = round((txTimeNs − head) / 13 600)`，再用字面量 `14 400` / `16 000`

### 2.3 三条路：代价、推荐、否掉另两条的理由

**路 (a)：就这么建，把「买不到」当成这一课的结论。**

- **代价**：§3 的改动量（六个常数、一个场景小节、`FrameDesc` 一个可选字段、
  四个函数多一个可选参数、一处正确性修正），加 §7 的课文；
  以及一个必须承受的风险：**读者可能觉得被耍**。
- **为什么它仍然是对的**：§2.2 的第一组与第二组是两条今天课程里没有、
  而且只有建出来才量得到的真事实（代价跨一个数量级；同一个旋钮在欠载场景里
  连代价都看不见）。再加上 §0.3——**这一课已发布的那条 `limits` 现在就是错的**，
  而把它改对的唯一办法就是把这三个取值真的跑一遍。
- **「觉得被耍」怎么拆掉**：不是靠措辞，是靠三件结构上的事。
  (i) **这一课不叫「保护间隔的权衡」，它是 `airtime` 那一课的第三个维度**
  （§7）——`airtime` 的 `why` 本来就是「一帧占多久空口」，而 GI 唯一被建模的
  作用正是空口时间。**一课只讲它建了的那一侧，就谈不上被耍。**
  (ii) **收益的缺席写在正文里，不只写在 `limits` 里**，并且带上 §1.3 的四个条号：
  标准自己只在四处提到时延扩展，而四处都没有数。
  (iii) **这一刀不开放基本 GI**（§3.3），所以场景里不存在一个「写了等于没写」的档位。

**路 (b)：不做，把这一刀换成别的。** 否掉。

要说清 4a §7.1 为什么判断错了——而**它没有判断错**，它只是把尺寸算小了
（§0.2 的三处）。4a 立案时的两个核心判断都成立：取值查得到（§1.1 坐实了表号与和式）、
不需要 σ_τ（§1.3 坐实了，而且比 4a 说的更强：标准连一句定性描述之外的话都没有）。
**而它要解除的那条 `limits` 不只是「待解除」，它是错的**（§0.3）。
**一条已发布的、能被四行算术证伪的课文，比任何新功能都更该先动。**

**路 (c)：先建一个让保护间隔买到东西的东西（某种时延扩展的代理）。** 否掉，
而且是**按「不许发明数字」那条准则硬性否掉**，不是按工作量。

要建这个代理，只有两条进路，两条都不过：

1. **直接给 σ_τ 一个值。** 4a 已穷举检索，两份文件零命中（§1.3 复核）。
   写进去只能标 `model`，而标了 `model` 就要说它是谁选的——**答案会是「我」**。
   而且它不是一个无害的 `model`：σ_τ 一旦有值，三个 GI 的**相对优劣**就全由它决定，
   **这一课的全部结论会挂在一个我编的数上**。这是本仓库最不该出现的那种数。
2. **从 4a 的格宽反推相干带宽。** 这条更危险，因为它看起来是从仓库里**已有的东西**推的。
   4a 把信道切成 2.03125 MHz 一格，照 B_c ≈ 1/(2π σ_τ) 反推就是 σ_τ ≈ 78 ns。
   **不行，两条理由各自致命**：
   - **B_c 与 σ_τ 的那个关系式在两份标准里零命中**（`coherence bandwidth` 全零，
     §1.3）。它是教科书的，不是标准的。用它等于把发明的数藏在一个公式后面。
   - **更要紧：4a 的 2.03125 MHz 不是相干带宽，它是一个上报粒度。**
     4a §1.2 自己逐字写明「它不是相干带宽——正文没有这个词」：
     那个宽度来自 §9.4.1.75 的「每 20 MHz 九个、每个是该 26 音调资源单元内逐子载波
     信噪比的算术平均」，是**标准选的回报分格**。
     把它当成相干带宽来反推，会让 4a 那个格宽**追溯地变成承重的物理量**——
     而 4a 明确把它立成了别的东西。**这是一次会反向污染已合并切片的改动。**

   **所以路 (c) 不是「以后再做」，它是「没有出处之前不做」**，并且这一句要进 §6.2，
   和 4a / 4b 的同一条合并记一处。

**还有一条我想到、也否掉的路 (d)：建成只读的、不进时间线的。**
即只加 §3.2 的六个常数与一个 widget，让读者在课文里看三列速率与三个空口时间，
**但任何非基本 GI 永不进入一条被跑的时间线**。
好处是 fixture 零风险、空转零风险（没有配置就没有空转的配置）。
**否掉的理由只有一条，而它是本仓库立过的规矩：一个特性不跑完一轮就不算做完。**
§2.2 第二组那两行——「350 条 PPDU、250 250 字节、空口时间 +15.11 %」
与「−11.41 %」——**只有真的跑才量得到**，而它们正是这一课最有价值的两个数。
路 (d) 会把这一课退回成一张表。

时 `(TLTF_4X_NS + TGI_NS.quad) - (TLTF_2X_NS + TGI_NS.base)` = **8 800**，否则 0——
依据是 §1.4 那张配对表，出处 `standard §27.1.1`、`§26.7.5` / `standard be §36.1.1`、`§35.7.5`。
**这个 8.8 µs 是算出来的，不是量出来的；而它的正当性靠的是 §1.4 末尾
那个前导码逐段加和（43.2 ≈ 44、47.2 ≈ 48）对得上。**

### 3.3 场景小节：缺省不存在，而且**只有两个合法值** · `model`（哪两个是我定的，理由在 §1.5 与 §5）

照 `fading` 与 `selectivity` 立的那条规矩（`src/model/scenario.ts:1034-1052`、`:1087-1124`）：
**缺省不是一个填了 base 的字段，而是整节不存在。**

```
guardInterval?: { gi: 'double' | 'quad' }
```

- `z.object({ gi: z.enum(['double', 'quad']) })`，**`.optional()` 且不带 `.default()`**，
  默认值落在**字段上、永不落在小节上**——这是 `fading` 的注释逐字立过的规矩。
- **没有 `'base'`。** 两条理由各自成立：
  (i) 写 `'base'` 的那份场景**与不写这一节逐字节相同**（§5 第 1 条），
  这正是本仓库反复发出的那种配置；
  (ii) 0.8 µs 是三档里唯一一个**对某种 PPDU 格式不强制**的（§1.5）。
  **schema 能拒的就在 schema 里拒，这一条 schema 拒得掉。**
- 字段叫 `gi` 而不是 `long` / `robust` / `mode`：**名字里不许出现任何
  暗示它买到了什么的词。**「double」「quad」是 Table 27-13 自己的 description 用词。

### 3.4 `FrameDesc` 多一个可选字段 · `standard §27.2 Table 27-1`

```
giNs?: Ns     // TXVECTOR 的 GI_TYPE；基本 GI 时**不出现**
```

**基本 GI 时字段缺席**，而不是写 800。两条理由：
`ppduLayout`（手上只有 `FrameDesc`，§3.1 那张表）需要知道这一帧的符号时长，

**这里不写行号，而 4a §8 第 1 条引的 `455-457` 正是不写的理由**：那个行号在 4b 合并之后
就失效了，写这份规格时它在第 627 行，而本刀给 `captureWindowNs` 补完注释之后又成了第 634 行
——两刀之内漂了两次。4a 那一处已经改成不带行号的写法。
以及它让记录与 UI 在已发布课程里**逐字符不变**（§4）。

### 3.5 一处正确性修正：`maxPsduBytesFor` 必须收 GI，否则上行会超预算

`mac.ts:171-178` 从一个**时长预算**反推能装多少字节：
`nsym = Math.floor((durNs - preambleNs) / symNs)`。
两个调用点都是上行触发式 PPDU 的定尺：
`mac.ts:964`（预算 `2_000_000 - signalExtNs`）与 `mac.ts:1494`（预算 `dur - signalExtNs`）。

**如果 GI 变长而这里仍除 13 600，算出来的 `nsym` 会偏大，
于是触发出来的 TB PPDU 会比它被允许的时长更长。**
所以 `maxPsduBytesFor` 的签名要加 `giNs`，而且这**不是修饰，是正确性**：
它是这一刀唯一一处「不改就会错」的地方。
**验收要有一条断言：`giNs` 为 quad 时，触发出来的每一条 TB PPDU 的
`txTimeNs ≤` 它那一次的预算。**

### 3.5b 第二处正确性修正：`captureWindowNs` —— **这一节是本规格漏掉的，补写于落地之后**

**这一条不在本规格原来的任何一节里，而它该在。** §3.1 那张表列了 `symNs` 的六个读取点，
而「前导码有多长」另有一组读取点，本规格只想到了 `txTimeModeNs`、`maxPsduBytesFor`、
`ppduLayout` 与 `FrameDetail`。**第七个在 `src/engine/channel.ts` 的 `captureWindowNs` 里**：

```
const captureWindowNs = (frame: FrameDesc): Ns => {
  …                                           // AMP 的几条各走自己的
  return PHY_MODES[frame.mode ?? 'nonht'].preambleNs      // ← 这一行
}
```

它的文档注释自己写着这是什么：「这一帧的前导码，在这段时间里射频还在做自动增益与定时捕获；
一旦进了载荷就 committed 了」。而**四倍 GI 下真实前导码是 52.8 µs 不是 44**，
所以读那个常数等于把前导码最后 **8.8 µs** 宣布成已 committed 的载荷——
在那一段里到达的更强信号本该还能被重新同步上去，却不能。
改成 `preambleNsFor(frame.mode ?? 'nonht', frame.giNs)`；
而 `preambleNsFor(mode, undefined)` 按构造就是那个常数，
**所以不写 `guardInterval` 的场景一纳秒都不动**，§4 的红线不受影响。

**而这一处第一次写出来是零覆盖的，这件事本身是证据。** 把 `frame.giNs` 这个实参去掉再跑全量
——**255 个文件全绿**。（顺带一提：仪器 B 从来没有暴露过这一处，不是因为它绕过了这个函数，
而是因为它改 `PHY_MODES.preambleNs` 时这个函数**自动跟着变了**——它读的就是那个字段。
真正没跟的只有 `PHY_MODES[*].mbps`，见 §2.2 那个方框。）也就是说本刀所有其它断言合起来也抓不住它，
正如本规格合起来也没想到它。补上的是一对判别用例（`tests/engine/channel.test.ts`）：
一条弱的四倍 GI 接收开始后 **48 µs** 有更强的信号到达，
48 µs **在 52.8 µs 的前导码之内、在 44 µs 的前导码之外**，
于是四倍档那一条必须捕获、基本档那一条必须不捕获。去掉实参，前一条当场红。

**给下一个人的判据，比这一处本身更有用**：这一刀改的是「前导码有多长」与「符号有多长」，
所以**凡是读 `preambleNs` 或 `symNs` 去回答一个关于时间的问题的调用点，都要问一遍它在四倍档下还对不对**
——而「任务的文件清单」上不会有它们。本规格 §3.1 的表只扫了 `symNs`，这是它漏掉第七处的直接原因。

### 3.6 决定二（`mbps`）：标准自己有三列，所以它是查的，不是算的 · `standard §27.5 Table 27-86` / `standard be §36.5.6 Table 36-76`

brief 给了三条路（从 `symNs` 现算 / 冻在 0.8 那档并在界面说明 / 别的）。
**答案是第三条，而它的形状是 §0.4 那张三列表。**

- **`mcsRateMbps(mode, mcs, giNs = TGI_NS.base)`** 返回
  `round(ndbps / (symNsFor(mode, giNs) / 1000), 1)`。
  **默认参数下与今天的字面量逐项相同**（仪器 C：14/14 与 12/12，零处不符），
  所以 `widgetModel`、`FrameDesc.mbps`、UI 的每一处显示在已发布课程里不动一个字符。
- **`FrameDesc.mbps` 在 `giNs` 在场时取那一档的列值。** 为什么必须这样：
  §2.2 量过一条真实的 `ofdma-dl` MU PPDU，`giNs` 为 quad 时它的 `txTimeNs`
  从 211 200 变成 ~~240 000~~ **248 800** ns，**而两个成员的 `bytes` 都还是 1434、
  `mbps` 都还印着 143.4**。（~~240 000~~ 是仪器 B 的数，它只加了符号那一项
  44 000 + 4 000 + 12 × 16 000；落地实现还要加 4× LTF 那 8.8 µs，前导码是 52 800，
  所以是 248 800。落地之后复核过：`bytes` 仍是 1434，而 `mbps` 现在印 **121.9**——
  这正是本条要修的那件事。）
  那正是本仓库的招牌故障：**一条记录说的速率被它自己的时间线证伪。**
  按 Table 27-86 它该印 **121.9**。
- **控制帧响应那条路必须保持对 GI 失明，而这不是妥协，是 §10.6。**
  §10.6 的规则走的是**非 HT 参考速率**，而参考速率由星座与码率决定
  （`NONHT_REF_MBPS`）——**保护间隔不改星座。**
  `ctrlRespRateForMode(mode, mcs, mbps)` 对 `he`/`eht` 本来就忽略第三个入参，
  `rtsRate`（`mac.ts:659`）与 `ctrlRespRateFor(frame.mbps)`（`mac.ts:1428`、`:1609`）
  看到的都是第 17 章的速率。**要有一条断言把这件事钉住**，
  因为「让 `mbps` 跟着 GI 走」最容易顺手破坏的就是它。
- **三列全印进课文。** `he` MCS 11：**143.4 / 135.4 / 121.9 Mb/s**；
  `eht` MCS 13：**172.1 / 162.5 / 146.3 Mb/s**（仪器 C）。
  **这是这一课最便宜的一个收获：读者第一次看到「速率」这个词原来有三个值。**

## 6. 明确不做：范围 / 举证，两类分开

### 6.1 范围决定（「一刀的量，和之后那一刀」）

- **HT / VHT 的 400 ns 短保护间隔。** 取值查到了：Table 19-6 / Table 21-5 的
  T_GI = 800 ns、T_GIS = 400 ns，`GI_TYPE` 在那两代里的枚举是 `LONG_GI` / `SHORT_GI`
  （不是 HE/EHT 的那三个值），Table 19-27 每一行都印着「800 ns GI | 400 ns GI」两列速率。
  **不做的理由是它是可选的**：§19.3.5 与 Table 19-27 的 NOTE 各逐字写明
  「support of 400 ns GI is optional on transmit and receive」，
  而 HE/EHT 那三档**全部强制**（§1.5）。
  **本刀只建强制的那一组**，`nonht`/`vht` 的 4 µs 符号一个纳秒都不动（§5 第 2 条）。
  顺带记一句：`PHY_MODES.nonht/vht.symNs = 4_000` 就是 T_DFT,Pre（3.2 µs）+ 800 ns，
  今天的注释没这么说，**这一句该补，但补注释不等于建功能。**
- **按信道**推出该选哪一档（一个 GI 选择算法）。**不在任何已排的刀里**，
  而理由有两层：标准不规定选择规则（只规定了存在哪三档、各档的符号时长、
  以及 `GI_TYPE` 由 TXVECTOR 指定），而**选择规则要读的那个量（σ_τ）没有出处**（§6.2）。
  所以这一刀的 GI 是**一个场景常量**，不是一个被推出来的量。
  **这件事要写成 `model-value`**：场景写哪一档是场景作者定的，引擎不替它选。
- **包扩展（T_PE）与 `NOMINAL_PACKET_PADDING`。** Table 27-13 给了 T_PE
  的五个取值（0 / 4 / 8 / 12 / 16 µs），而引擎整个不建包扩展
  （`frame-anatomy-bytes` 的 `limits` 已记过）。
  它和 GI 共用「PPDU 尾部多一段时间」这个形状，**而它是另一刀**：
  T_PE 的取值由接收端的能力与 `PRE_FEC_PADDING_FACTOR` 决定，
  那是一条 MAC 协商，里面一个符号都没有。记在这里是为了下一个人不要以为 4c 顺手做了它。
- **midamble。** §27.1.1 提到 HE PHY 支持 midamble，用途是 PPDU 期间更新信道估计，
  「might be of use in high mobility scenarios」。**它和长 GI 是同一类对抗手段
  （都是花时间换稳健），而引擎既不建信道估计误差、也不建移动**（节点在一轮里不动）。
  **所以 midamble 在这个引擎里和长 GI 一样买不到东西，而它连代价都还没有出处**
  （每几个符号插一次由 `MIDAMBLE_PERIODICITY` 定）。不做。
- **4× LTF 本身买到的那样东西（更好的信道估计）。** §3.2 把 4× LTF 的
  **时间代价** 8.8 µs 建了进来，因为它是 §1.4 那条配对的必然后果。
  **而它的收益同样不建**：引擎没有信道估计误差这个量。
  **这一句必须和 GI 的那一句并列写进 `limits`，不能只写 GI 那一句**——
  否则读者会以为 8.8 µs 是白付的。
- **`ofdma-dl` 那个 `MU_SYMBOLS = 12` 的定长 MU PPDU。** 它让 GI 只改 PPDU 的长度
  而不改它装多少比特（量过：`giNs` quad 时同一条 MU PPDU 的 `txTimeNs`
  211 200 → ~~240 000~~ **248 800** ns，两个成员的 `bytes` 都还是 1434）。
  **这不是缺陷，是那一课的场景就这么定的**；但它让 `ofdma-dl` 成为第二个
  「吞吐不动、空口时间涨」的场景。
  ~~量过：空口 80.55 → 88.10 ms，**+9.4 %**；送达字节 2 269 938 → 2 269 986，**+0.002 %**；
  两轮 `RX_FAIL` 都是 0。~~
  **划掉的这三个数是仪器 B 的第 3 行**——「3.2 µs GI 配 2× LTF」，而 §1.4 的配对让
  引擎永不发出那一档（判据见 §2.2 那个方框）。同一段里那个 240 000 ns 自己就是证据：
  44 000 + 4 000 + 12 × 16 000，前导码没加 4× LTF 的 8.8 µs。
  （**第二轮我在这里写的理由是「仪器 B 没改落地实现的三处」，那是错的**：那三处里
  `maxPsduBytesFor` 与 `captureWindowNs` 读的就是仪器 B 改掉的那两个全局量，自动跟着变了。
  数该换，理由不对，两件事。）
  **用落地实现重量（本课自己的场景、`runUntil(150 ms)`、默认种子、基本档对四倍档）：**
  - **一个 MU PPDU 自己**：211 200 → **248 800 ns**（**+17.8 %**）；
  - **整轮所有 PPDU 的空口时间**：80.55 → **92.43 ms**（**+14.7 %**，比上一个小，
    因为这一轮里还有不变长的单用户帧与确认帧）；
  - **真正送出去的 MSDU**：两档都是 **529 个**，`RX_FAIL` 两档都是 0。
  **第三个数要按出队的 MSDU 数，不能按各接收端收到的字节之和**：一个 MU PPDU 会被它的每个
  成员各收一次，按接收端求和会把同一份载荷数好几遍，而重复的倍数还随分组人数变
  （量过：MU 接收 66 → 81）。同一个场景按 `msduBytes` 求和给出 −2.06 %、按 `bytes` 求和给出
  +0.005 %，两个互相打架——**两个都是坏尺子**。
  **本刀不改那个场景**，只在 `ofdma-dl` 的 `limits` 里记一句。
- **记录流里多一个 `WIFI_GI` 之类的新记录类型。** 不加。
  GI 是 PPDU 的属性，`TX_START`/`RX_OK` 已经带着 `FrameDesc`，
  §3.4 的 `giNs` 够了。**加一个新记录类型会动 `updateHash` 吃的那个 `type`，
  而那正是 §4 唯一的红线。**

### 6.2 举证不足（「正文没说」）

- **时延扩展 σ_τ 的任何取值，以及任何一张信道模型表。** 4a §1.4 的穷举检索我复核过
  （§1.3），结论不变并且更强：四处提及 `delay spread` 的句子是同一句，
  说的是 GI 对抗它，**而全书没有一个 σ_τ 的数、没有一张功率时延谱**。
  **这一条和 4a / 4b 的同一条合并记一处**，而 4c 要加的是另半句：
  **4a 说「这一刀不需要它」，4c 必须说「这一刀需要它、而它没有，所以这一刀只建代价」。**
  两句不是同一件事，混成一句就是多径那份规格在 UWB 那半犯过的错。
- **相干带宽与 σ_τ 之间的任何关系式。** `coherence bandwidth` 在两份文件里零命中。
  `coherence` 的两页（§10.33.3 与其 CMMG 对应节）说的是**相干时间**，
  而且是一条没有数值的定性 NOTE（4a 已读，我复核）。
  **所以从 4a 的 2.03125 MHz 反推 σ_τ 这条路，缺的不是一个数，是整个关系式。**
  这一条要和上一条分开记（一个是「缺一个数」，一个是「缺一个公式，而且反推会污染 4a」，
  §2.3 路 (c) 第 2 条）。
- **信道估计误差的任何量。** 4× LTF 与 midamble 的收益都挂在它上面，
  而标准给的是训练字段的**时长与序列**，不是估计误差的方差。
  **这一条是「有机理、缺一个数」，与上面两条不同。**
- **「哪一档 GI 该配多长的包扩展」。** Table 27-13 给 T_PE 五个取值，
  但哪一档配哪一个由能力字段决定，而本刀不建能力协商。

## 7. 课程落点

### 7.1 判断：挂在 `airtime` 上，**不新开一课**

brief 已经指出 `selectivity` 与 `ru-diversity` 都在 30 分钟上限，所以挂不上去。
剩下的选择是「新开一课」或「挂在既有课上」。**挂在 `airtime` 上，三条理由：**

1. **一门新课要有自己的 `why`，而这一刀唯一诚实的 `why` 是一句元命题。**
   「为什么真实设备仍然愿意付这笔钱，而这里看不见它」不是一个 Wi-Fi 题目，
   它是一个关于这个仿真器的题目。**一门 20 分钟的课，题目是「这个旋钮买不到东西」
   ——那才是会让读者觉得被耍的形状。**
2. **`airtime` 的 `why` 已经是「一帧占多久空口」**，而 GI 在这个引擎里被建模的
   作用**恰好只有空口时间**。所以这不是把 GI 塞进一课，
   **是把 GI 放回它唯一有内容的那一课。**
3. **`airtime` 自己的正文已经走到了门口。** 它现在逐字印着
   「拿 125.6 µs 的色块减去 44.0 µs 的前导码，再把剩下的除以 13.6 µs。
   你应该刚好得到六个符号。」**那个 13.6 就是 T_SYM1**，
   而这一刀要补的正是「它还可以是 14.4 或 16」。

## 9. 判断：这一刀该不该按这个样子做

**该做，按路 (a) 做，挂在 `airtime` 上，落 25 分钟，fixture 只加一行。**

而要说清五件与 brief / 4a 不同的事：

1. **brief 把这一刀的风险定成「它花掉空口时间，而什么都买不到」，
   而真正的风险比这个更具体：它会假装买到了东西。**
   §2.2 第三组量出来，同一个旋钮在 `capstone` 上让丢帧率从 5.44 % 掉到 4.57 %、
   在 `ru-diversity` 上从 14.29 % 涨到 17.86 %、在 `rate-cost` 上非单调。
   **而 §2.1 证明了解调门限对 GI 失明是签名级的事实。**
   所以这一刀最该防的不是「空转」，是**一条写得像物理的噪声断言**。
   §5 第 6 条与 §8 第 4 条是为这件事准备的，而那条文本守卫是硬闸门。

2. **「买不到」这件事能被精确地说成一句有出处的话，而这改变了它的性质。**
   `delay spread` 在 802.11-2024 的 5956 页里命中 3 页、在 802.11be-2024 的
   1020 页里命中 1 页，四页是同一句：GI 对抗时延扩展（§19.3.20 / §27.3.23 /
   §32.3.13 / be §36.3.22）。**标准说了它买什么，却从不给那样东西一个数。**
   于是「这里看不见它」不是我们省略了一个可查的量，
   **是标准本身只发布了这笔交易的一侧。** 这句话该是这一课的结论，
   而它比任何编造的权衡都更诚实、也更有信息量。

3. **代价这一侧比 brief 和 4a 预期的都更有内容，而内容在「它跨一个数量级」上。**
   逐 PPDU 量出来（仪器 A，9463 条）：双倍 GI 的代价从 **+1.22 % 到 +5.82 %**，
   四倍从 **+3.66 % 到 +17.47 %**，**而决定它的是这一帧有几个符号（1 到 316）**。
   把 §1.4 那条前导码绑定算进去，这个跨度**塌成 +17.07 % 到 +19.44 %**——
   因为前导码那一项与符号那一项正好互补。
   **这个塌缩是这一刀最漂亮的一个结果，而它只有把 4× LTF 建进来才看得见。**
   4a §7.1 的「一两成」只在这个前提下才对。

4. **brief 的「技术决定二」有一个 brief 不知道的答案，而答案在标准里。**
   Table 27-86 / Table 36-76 的速率栏是**三列**（0.8 / 1.6 / 3.2 µs GI），
   而 `PHY_MODES.he/eht.mbps` 就是第一列（量过：14/14 与 12/12，零处不符），
   连 `Math.round(x*10)/10` 这个取整约定都是 §19.5 的原话。
   **所以 `mbps` 既不该「从 `symNs` 现算」也不该「冻住再加个界面说明」——
   它该变成一张三列表的查询，而默认列与今天逐项相同。**
   而 §10.6 那条控制帧响应的路必须留在非 HT 参考速率上，**这不是妥协，是条号。**

5. **4a §7.1 的「一个新常数都不要」是这一刀里最该被纠正的一句，而纠正的方向是放心的。**
   要六个常数（§3.2），**六个全有表号，零个 `model`**。
   4a 想说的是「不需要发明」，它说成了「不需要新增」。
   而 4a 真正判断错的那一处在它的 §1.4：HT 那一句的条号是 **§19.3.20**，
   不是 §19.3.2/§19.3.3。**那张表是 4a 整份规格的立论基础（σ_τ 查不到），
   所以它的条号该是对的。**

**而要承认的一件事**：这一刀最可能失败的地方不是实现，也不是 §7 的场景
（`airtime` 自己的场景干净得出奇——四档下 350 条 PPDU、250 250 字节逐个相同，
零丢帧零丢包，而空口时间 +15.11 %，一次噪声都没有）。
**最可能失败的地方是 §8 第 4 条那条文本守卫被当成形式。**
一个只有代价的旋钮，摆在一个会重采样的仿真器里，
**它的收益会自己长出来**——`capstone` 那四个数就是它长出来的样子。
**守卫不立，这一课会在它发布之后的某一次「验证」里变成一条假结论，
而那一次没有人会怀疑尺子。**
