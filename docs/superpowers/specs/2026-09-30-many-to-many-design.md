# 多对多测距：一次发送同时是问也是答

2026-09-30。已发布标准 §10.32.6（SS-TWR）与 §10.32.7（DS-TWR）的多对多测距。
`docs/uwb-modellable-backlog.md` 的切片 2。

## 1. 为什么它值得做，而且值得做在第二位

这是整个 UWB 课程里**空口效率差得最悬殊的一对**，而且那个差距是一个可以算出来的
整数倍。

引擎今天只会一对多：一个标签问，N 个锚点答。要让 N 台设备**两两**都知道距离，
就得让每台设备轮流当一次标签——N 轮，每轮 N 个时隙，一共 **N² 个时隙**。

多对多把它压成 **N 个时隙**。

原理只有一句话：**参与者 i 那一次发送，对排在它后面的每个人是「问」，
对排在它前面的每个人是「答」。** 一次发送干两份活，于是 N 次发送就够了。

| 方案 | 时隙数 | 量到的距离数 |
| --- | --- | --- |
| 一对多 SS-TWR，轮流当标签 N 次 | **N²** | N(N−1)/2 |
| 多对多 SS-TWR §10.32.6 | **N** | N(N−1)/2 |
| 多对多 DS-TWR §10.32.7 | **2N** | N(N−1)/2 |

N = 6 时：36 个时隙对 6 个时隙，量出同样的 15 条距离。**整整 N 倍。**

这个数是这一刀的验收：不是"多对多能跑"，而是"同一组设备、同样多的距离、
时隙数之比正好是 N"。

## 2. 谁能算出距离，以及为什么只有一边能

这是本刀最反直觉、也最该写成一课的地方。

记参与者 0…N−1，参与者 i 在时隙 i 发送，帧里带**它自己的发送时刻**与**它收到
时隙 0…i−1 每一次发送的时刻**。

看一对 (i, j)，i < j：

- i 在 `T_i(i)` 发，j 在 `T_j(i)` 收到。
- j 在 `T_j(j)` 发，i 在 `T_i(j)` 收到。
- **j 的帧里带着 `T_j(j)` 与 `T_j(i)`**——因为 i 排在 j 前面，j 发的时候已经收到过 i。

于是 **i 手里有四个时间量全部**：`T_i(i)`、`T_i(j)`（自己量的），
`T_j(j)`、`T_j(i)`（j 的帧带来的）。往返时间与回复时间都齐了，
`ranging.ts#ssTwrCorrected` 直接算。

**而 j 算不出来。** j 需要 `T_i(i)` 和 `T_i(j)`，前者 i 的帧带了，
后者是 i 收到 j 的时刻——那件事在 i 发送的时候**还没发生**。

所以：**每一对距离，只有排在前面的那一个算得出来。** 参与者 0 算出 N−1 条，
参与者 1 算出 N−2 条，……参与者 N−1 算出 0 条。加起来正好 N(N−1)/2。

这和切片 1 的 §7「谁手里有距离」是同一件事的另一面，两课可以互相指。

## 3. DS 的多对多：两趟，不是两倍的帧

DS-TWR 需要四个时间量里多出来的那两个（`tround2`、`treply2`），
它们要求 **i 发第二次**。所以多对多 DS 是**两趟**，每趟 N 个时隙：

```
第 1 趟：参与者 0…N−1 各发一次
第 2 趟：参与者 0…N−1 各再发一次，帧里带第 1 趟与第 2 趟已经听到的接收时刻
```

对 (i, j)、i < j：i 有 `A_i`、`B_i`（自己两次发送），`T_i(A_j)`；
j 的第 1 趟帧带来 `A_j` 与 `T_j(A_i)`，j 的第 2 趟帧带来 `B_j` 与 `T_j(B_i)`
（j 的第 2 趟排在 i 的第 2 趟之后，所以它来得及）。四个量齐，`ranging.ts#dsTwr`。

2N 个时隙，N(N−1)/2 条 DS 距离。仍然是**只有排在前面的那一个算得出来**。

## 4. 帧：它是 DL-TDoA 的内容，用在双向测距上

参与者 i 的帧要带自己的发送时刻，加 i 个接收时刻。**引擎里已经有这个形状**：
DL-TDoA 的 Final 就是「自己的发送时刻 + 收到每个响应的时刻」，
`phy.ts#DL_TX_TIME_IE_BYTES`、`phy.ts#dlRxTimesIeBytes`、`frames.ts#UwbDlTimes`。

复用是诚实的，因为内容真的一样；但那几个名字带着 `DL_` 前缀，
而多对多不是单向测距。**实现者判断**：复用并加注释说明为什么，
或者把那几个常量改成中性名字并更新 DL-TDoA 的引用。改名的代价是一次纯机械的
波及，收益是名字不再撒谎——倾向后者，但由实现者看过调用方之后定，并在报告里说理由。

**时钟偏移不进帧。** 现有的 SS 路径里 `coffs` 是接收端自己量出来的
（`onResponse` 的 `coffs` 参数来自 `UwbRxInfo`，不是来自帧），多对多照旧：
i 收到 j 的帧时就量到了 j 相对自己的偏移。省一个 IE，而且与既有路径一致。

于是帧长是 `MHR 9 + RRMC 3 + 发送时刻 IE 6 + 接收时刻 IE (2 + 4k) + FCS 2`，
k 是它带的接收时刻个数。**最后一个参与者带 N−1 个**，所以它是全轮最长的帧——
和嵌入式 DS 的 Final 一样，**它就是那个决定参与者上限的东西**。
上限照切片 1 的办法**算出来**，不许写成字面量：`uwbMaxAnchors` 已经是这个形状了。

## 5. 参与者名单：顺序必须是确定的，而且与角色无关

多对多里**没有标签也没有锚点**——每台设备两种活都干。但场景里的节点仍然带
`uwb.role`，而且编辑器与场景图要用它画图。

决定：**`m2m` 模式下每一个 UWB 节点都是参与者，顺序按节点 id 排序**，
`role` 只影响怎么画。

顺序按 id 排而不是按场景里的节点顺序，理由是确定性：节点顺序会被编辑器的增删改动，
而那会让同一个场景换一个时隙分配、换一份时间线哈希。**这是一个模型决定
（`model`），标准让排定表决定谁占哪个时隙，而本仿真器没有排定表可商量。**

schema 因此要改一条：UWB 会话现在要求至少一个标签，**而 `m2m` 不需要**。
那条规则要按模式分开，消息里说清 `m2m` 为什么不需要。

一个块装一轮，全组共用（和 DL-TDoA 一样），不是「每个标签一轮」。

## 6. 听不到就没有

参与者 i 若没收到参与者 j 的发送（墙、距离、碰撞），它的帧里就少一个接收时刻，
那一对就没有距离。**这不是错误路径，这是多对多正常的样子**——而且它是这一课
第二个值得读的地方：一对多里丢一个锚点只丢一条距离，多对多里排在前面的人丢一次
发送，丢的是它与后面所有人之间的那一条。

要测出来：把一台设备挪到墙后，数少了几条 `UWB_RANGE`，并对上「它本该算出几条」。

## 7. 不做，以及为什么

- **§10.32.8 的 SP3 分组测距，以及它的 SRRR IE。** 留在债里，理由是举证不足：
  本仓库只抽了已发布标准的**目录**，SP3 分组测距的机理无从建立。
  已知的是 SP3 这个包配置本身（SYNC + SFD + STS，无 PHR 无载荷，所以它**带不了时间**），
  而「一组设备如何用带不了时间的包完成测距」这一步，语料库说不出来。
  **repo 的规矩是不抄标准正文、也不猜机理**，所以这一条不在本刀里，
  并且要在覆盖表里把这个理由写下来——它和「范围决定」不是一回事。
- **多对多的安全（§10.31/§10.33）** 照旧不建：本仿真器没有一处密码学。
- **多对多的 IE 控制位**（ARC、RDM 的加入/退出管理）照旧只建长度不建布局，
  与既有的多节点 IE 行一致。

## 8. 验收：跑完整轮，读它的输出

1. **N 倍那个数。** 同一组 N 台设备：多对多一轮 N 个时隙，数出 N(N−1)/2 条
   `UWB_RANGE`；一对多轮流当标签 N 次，数出同样多条，用掉 N² 个时隙。
   **两个时隙数之比等于 N**，对 N = 3、4、6 各验一次。
2. **距离本身是对的。** 每一条 `UWB_RANGE` 对上几何真值，误差在噪声之内。
3. **只有排在前面的那一个算得出来**（§2）：读记录的 `node` 字段，
   参与者 i 恰好有 N−1−i 条。
4. **DS 多对多是 2N 个时隙**，量出同样多的距离，而且比 SS 更准
   （晶振拉开 ppm 时——和切片 1 同一个理由）。
5. **听不到就没有**（§6）：一台设备移到墙后，少掉的距离条数与预期一致。
6. **参与者上限是算出来的**：最后一个参与者的帧长 ≤ 127 字节的最大 N，
   两侧边界都钉住。
7. **既有场景逐字节不变**，两份 fixture 零 diff。
