# SP3 分组测距：最短的测距帧，不构成最短的轮

2026-10-02。已发布标准 §10.32.8 与它的 SRRR IE（§10.32.9.9）。
`docs/uwb-modellable-backlog.md` 的切片 3.5。

## 1. 机理（正文读出来的，不是从标题猜的）

§10.32.8.1：SP3 测距分**三个相位**——RCM、SP3 测距、数据报告。

§10.32.8.2 讲清了三件要紧的事：

- **身份来自时隙，不来自载荷。** 调度由控制器的上层决定，每个时隙指派给一台确定的
  设备，而 RCM 里的 **RDM IE** 就是承载"哪个时隙归谁、角色是什么"的那个单元。
- **ARC IE 指定测距过程与 SP3 包格式**，于是两端都知道 SP3 相位何时开始、何时结束，
  并在前后各调一次 MLME-STS 原语启停这个包配置。
- **RCM 可以携带 RSSD IE** 交换 STS 种子的一部分；而参与设备的 **STS 计数器必须为
  SP3 包的收发各自推进并设对**。

而 **SRRR IE**（§10.32.9.9，SP3 Ranging Request Reports IE）是**响应方请求要报什么**：
正文的例子里 `SRRR IE (I,R1)` 表示响应方 1 向发起方请求到达角与往返时间，
把该单元的 **RAOA** 与 **RRTT** 两个字段都置 1。

## 2. 这一刀真正要教的东西

一个 SP3 包是 `SYNC + SFD + STS`：**没有 PHR，没有载荷**。所以它是一个纯粹的
时间标记——而正因为它带不了载荷，**它量到的时间必须在别的地方回来**。

于是它和切片 1 直接咬合：那一刀建的 **SS-TWR 回复时间延后**（§10.29.6.3）正是
"先发，时间随后由另一条消息补上"那条路。**SP3 把这条路上的测距帧压到物理上最短。**

而账是这样的（本仿真器的既有常量，Task 1 要跑出来而不是抄）：

| 帧 | 码片 | 约 |
| --- | --- | --- |
| SP3 测距标记 = `UWB_SHR_CHIPS + UWB_STS_CHIPS` | 70 368 | **141 µs** |
| 最短的 SP1 帧（14 字节响应，含 PHR） | — | **181 µs** |

每个测距帧省约 **40 µs**。但：

- SS-TWR 嵌入式（SP1）：A+1 帧，**没有报告相位**。
- SP3 分组：A+1 个标记，**外加 A 个报告**。

**所以 SP3 是否划算取决于 A 与报告的大小，而不是取决于哪一帧更短。**
这就是那一课的题目：**最短的测距帧不构成最短的轮。**
Task 1 要把这个交叉点算出来——A 等于几时 SP3 开始划算。

## 3. 建什么

### 3.1 SP3 包

`uwbSp3Chips()` / `uwbSp3Ns()` = `UWB_SHR_CHIPS + UWB_STS_CHIPS`，**不含 PHR**。
引擎的 `UwbInfo` 已经有 `sp` 字段（目前恒为 1，4ab 的控制面用 0），SP3 就是 `sp: 3`。
自己的 `FrameKind`：`'uwbSp3'`。

**不建 STS 本身**，照旧——引擎没有一处密码学，`UWB_STS_CHIPS` 建的只是"它占多少
空口时间"。`sts` 相关的 `limits` 已有先例，照抄那条理由。

### 3.2 身份来自时隙

这一条**引擎已经有了**：`slotAction` 就是"哪个时隙归谁"。SP3 不需要新机制，
它需要的是**不要给那一帧加任何能装身份的东西**——这是这一刀最容易被"顺手修好"
的地方，和切片 3 的 Ruling 3 同一个形状。

### 3.3 SRRR IE：请求要报什么

内容按正文：**RAOA** 与 **RRTT** 两个请求位。两者都对上了引擎已有的东西——
`aoa` 会话开关算出的方位角，以及 DS-TWR 的往返时间。

于是它建成**响应方在 RCM 之前声明自己要什么**，而报告相位只报被请求的那几项：
`RAOA` 关着就不报方位角，报告帧因此更短。**这是一个能量出来的数。**

`SRRR_IE_BYTES` = 头 2 + 控制 1（两个请求位 + 保留）= 3 字节，每个响应方一个。
RCM 因此长 `3A` 字节——**请求不是免费的**，与 §10.36 的 MMRCR 恰好相反
（那一位在既有的控制字里）。两者放在一起是一对好对比，课程要写。

## 4. 不做

- **MLME-STS 原语**与 **RSSD IE**：照旧，没有一个 MAC 原语，也不持密钥。
  STS 计数器的推进因此也不建——引擎的 STS 只是一段空口时间。
- **多发起方多响应方**（§10.32.8.1 说过程可推广到此）：本刀只建一对多，
  与 §10.32.8.2 的图一致。多对多已有自己的模式，两者的合并是另一刀。
- **SP2**：标准还有 SP2（STS 在载荷之后）。不建，范围决定：引擎不建调制与波形，
  SP2 与 SP1 在"占多少空口时间"这个粒度上没有差别。

## 5. 验收

1. **SP3 帧比最短的 SP1 帧短约 40 µs**，而且这个数是**跑出来的**
   （`uwbSp3Ns()` 与 `uwbPpduNs(uwbRespBytes('ds'))` 之差）。
2. **交叉点。** 同一场景，SP1 嵌入式与 SP3 分组各跑一轮，读整轮的空口时间总和：
   A 小的时候 SP3 更贵（报告相位的固定开销），A 大的时候更便宜。
   **把那个 A 算出来并写进课。**
3. **SP3 帧一个字节的载荷都没有**：`ies` 为空，帧长 = `uwbSp3Ns()` 对应的字节等价物
   不存在（它不是以字节计的），所以测试要直接比 ns。
4. **测距结果仍然正确**：SP3 轮测出的距离与 SP1 轮在噪声之内一致。
5. **SRRR 的请求位真的省东西**：`RAOA` 关掉时报告帧更短，差值等于方位角那一项。
6. **既有场景逐字节不变**，两份 fixture 零 diff。
