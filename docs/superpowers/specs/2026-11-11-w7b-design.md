# W7b 设计说明：EDCA/QoS、游戏模式、AMP（2026-11-11）

对照 IEEE Std 802.11-2024（下称「标准」）与 P802.11bp 的规范框架、草案文本（PDT）。计划见
`docs/superpowers/plans/2026-11-11-wifi-standard-alignment.md` 的 W7b 一节。硬规则：标准或已采纳的
草案文本里没有的信息单元、字段、帧、规则一律不实现；做不到就删除，② 写「未实现」。

## 1. 接入点用 dot11QAPEDCATable（§10.2.3.2，附录 C）

- 新常量 `engine/phy.ts#QAP_EDCA_PARAMS`，取附录 C 中 dot11QAPEDCATable 各列的缺省值：
  CWmin 15/15/7/3（与表 9-194 相同），CWmax 1023/63/15/7（aCWmax、4·(aCWmin+1)−1、aCWmin、
  (aCWmin+1)/2−1），AIFSN 7/3/1/1，TXOP 限制按表 9-194（2.528/2.528/4.096/2.080 ms）。
- `WifiMac` 在 `cfg.isAp && cfg.edca` 时用这张表，非 AP 站点仍用 `EDCA_PARAMS`（表 9-194）。
  标准：「The parameters used by the EDCAF … are defined by dot11QAPEDCATable at the AP and by
  dot11EDCATable at the non-AP STA」；§10.23.2.4：AIFSN 对非 AP 站点 ≥ 2，对 AP ≥ 1。
- 篡改驱动仍只作用于站点。

## 2. 每帧的用户优先级决定接入类别（§10.2.3.2，表 10-1）

- `Msdu.up`（0–7）随帧下传；`ac` 由 `model/frames.ts#acForUp`（表 10-1：UP 1、2 → BK，0、3 → BE，
  4、5 → VI，6、7 → VO）得出。QoS 数据帧的 TID 就是这个 UP（`MpduHdr.tid`，接收端去重按它）。
- 业务档给哪个 UP 由本仿真器决定（标准说用户优先级来自上层，表 10-1 的 Designation 列只是「一般用法
  与指导」）：语音 6、视频与手机互传视频 5、备份与物联网 1，浏览、饱和源与游戏 0
  （`engine/traffic.ts#upForProfile`）。这组取值与旧的「业务档 → AC」完全对应，所以除游戏模式外
  没有场景因此改变。
- 篡改驱动的 `allAsAc` 现在改写的是 UP（改为该 AC 的 TID_FOR_AC 值），AC 仍由 UP 得出，
  于是一个 A-MPDU 里不会混入两个 TID。

## 3. 生存期：DCF 与 EDCA 分开（§10.4，§10.23.2.12.1，附录 C）

- EDCA：dot11EDCATableMSDULifetime / dot11QAPEDCATableMSDULifetime，DEFVAL 500 TU = 512 ms，从交给
  MAC 时起算（原来取 ns-3 的 500 ms）。
- DCF（链路没有协商 EDCA）：dot11MaxTransmitMSDULifetime，DEFVAL 512 TU = 524.288 ms，「starts on the
  initial attempt to transmit the MSDU」（§10.4）——从第一次发送起算，所以从未发出的帧不会过期。
  `Msdu.firstTxNs` 在帧第一次上空口时记下（数据帧本身，不含 RTS）。
- 场景的 `queue.lifetimeMs` 在 EDCA 链路上设前者、在 DCF 链路上设后者。

## 4. 内部碰撞与 QSRC（§10.23.2.2，§10.23.2.12.1，§10.3.3）

- 发现单（B1）说「引擎在内部碰撞时还给落败帧记一次重传，而 §10.23.2.2 d) 只更新 QSRC 与 CW」。
  对照语料后**这一条不成立**：§10.23.2.12.1 明文规定「For internal collisions, the frame retry
  counts associated with the MSDUs … involved in the internal collision shall be incremented」，
  重传计数也受 dot11ShortRetryLimit 约束。引擎原来的做法是对的；`@edca` 的 ② 把它标为「与标准不同」
  是课文错了，改为「照标准」。
- 核对中发现的真正偏差：EDCA 的 QSRC 规则。§10.23.2.2：「If QSRC[AC] is less than
  dot11ShortRetryLimit, QSRC[AC] shall be incremented … Else QSRC[AC] shall be set to 0 [and]
  CW[AC] … to CWmin」——第七次连续失败把 QSRC 加到 7、CW 停在 CWmax，第八次失败才复位。引擎原来
  先加一、到 7 就复位，早了一次。现在 EDCA 按 §10.23.2.2；DCF 仍按 §10.3.3（「CW shall be reset to
  aCWmin … when SSRC reaches dot11ShortRetryLimit」），即到 7 就复位——两条规则在标准里本来就不同。

## 5. 路由器「游戏模式」删除（§11.25.3 MSCS 未实现）

- 原来的 `NodeCfg.gameAccel` 是接入点上的一个布尔，不交换任何帧就把游戏手机的上行与接入点给它的下行
  一起移到 AC_VI。标准里没有这样的机制。标准的对应物是 MSCS（§11.25.3）：由站点发起（MSCS
  Request/Response，Robust AV Streaming Action 帧与 MSCS Descriptor 元素），接入点只为下行 MSDU 按
  站点上行帧的 UP 设置优先级。实现 MSCS 需要管理帧（Action 帧）的收发，而管理帧在本引擎里整体未实现
  （W7a 范围外），所以按硬规则**删除**游戏模式：类型、schema、编辑器复选框、i18n、拒绝规则
  （`driverRefusalsFor` 的第一条）、场景选项 `cloudGameScenario({ accel })` 一并删除。
- 旧场景文件里的 `gameAccel` 仍能载入：zod 对象默认去掉未知键，字段被丢弃。
- `@wan-rtt` 的 ② 加一行「MSCS（§11.25.3）」，kind `absent`。

## 6. AMP（P802.11bp）

### 6a. 每个传输机会都不超过 AC_BK 的 TXOP 限制（§10.23.2.9，表 9-194）

- 去掉 `mac.ts#transmitFor` 里「AMP 轮不受 TXOP 限制约束」的豁免。轮自己按接入点 AC_BK 的
  TXOP 限制（dot11QAPEDCATableTXOPLimit，缺省 2.528 ms；接入点没有 EDCA 时取同一缺省值作上界）
  安排内容。
- Active Tx（`engine/ampAp.ts`）：一轮欠 `slots` 个随机接入时隙（twoPhase 再加每个听到的标签一个调度
  时隙）。每个传输机会只发一帧触发帧，它的 Number of Slots 取「CTS-to-self + SIFS + 触发帧 +
  N × (AMP SIFS + 时隙 + AMP SIFS + Ack) ≤ 限制」的最大 N；剩下的时隙在下一个 AC_BK 传输机会里继续，
  会话号不变。草案让接入点自由选择 N（§39.3.2.1），每帧触发帧都让标签重新抽 ABOC（§39.4），调度型
  触发帧只列出它分配时隙的那几个标签——没有用到任何草案之外的规则。CTS-to-self 的 Duration 覆盖这一个
  传输机会的触发帧、时隙与 Ack。250 kb/s、四个带读数的时隙：每个传输机会两个时隙。
- 单站反向散射（`engine/ampReader.ts`）：每帧都检查整个 PPDU（应答在 BST-Excitation 之内）能否在
  限制之内结束，放不下的留到下一个传输机会。原来的 `txopMs`（缺省 4 ms）删除。
- 轮询时钟的一次「轮」若还没做完，新的轮等它做完再开始（与原来清点的处理相同）。

### 6b. 单站反向散射按 PDT 11-26/1519r5 §39.3.3 重建

- 删除按提案 11-25/0061r0（未被采纳）实现的 EPC Gen2 Query/QueryRep/ACK、2^Q 个槽、RN16 句柄、
  计数跨传输机会保留（「Extend」）。
- 现在的流程，全部来自草案文本：
  1. 广播 AMP Trigger（ID 0xFFFF；随机接入，带会话号与 ACWE；只分配一个时隙；带上行速率），
     §39.3.3。帧格式沿用 Active Tx 触发帧的宽度（草案没有给出字段宽度，取值「model」）。
  2. 标签按 §39.4 每帧触发帧重新在 [0, 2^ACWE − 1] 里抽 ABOC，ABOC 小于时隙数（单站时为 1）即 0 时，
     在 BST-Excitation 里反射一帧 AMP Response（表 9-742 类型 3），带自己的 16 位标识（FM-25：EPC 的
     CRC-16）。
  3. 接入点「可以再用单播帧向某个标识征求应答」（§39.3.3）：对每个听到、尚未读过的标识，发一帧
     AMP RFID 帧（动议 #239，PDT 11-26/1520r3：MAC 头 32 位 = 帧控制 8 + ID 16 + 类型相关控制 8，
     FCS 16 位），帧体是 UHF 命令 Read（MM-29），读 EPC 存储区；标签以 AMP RFID 帧反射 Read 应答，
     带回 EPC。应答与命令在同一个传输机会里（PDT 11-26/1798r1）。
  4. 收到应答后不发下行 Ack（FM-35）。
- 配置改为 `acwe`、`slots`（一次清点的触发帧数）、`read`；旧场景的 `q` 载入时换成 `acwe = q`、
  `slots = 2^q`，`txopMs`、`write` 被丢弃。
- 记录：`AMP_BS_COUNTER` 删除，标签发 `AMP_ABOC`（与 Active Tx 同一种记录）；`AMP_RFID.cmd` 为
  `trigger` / `read`，带 `acwe`；`AMP_INVENTORY` 加 `ids`（AMP Response 里解出的标识）。
- 未实现：Select（可选，动议 #241；本读写器按听到的标识寻址）、Write（处理时延 ≥ 2 ms，
  1.1 × 2 ms 的 BST-Excitation 已超出 2.528 ms 的传输机会）、Authenticate；组确认与双基地反向散射。
- 发现：在 2.528 ms 的传输机会里，带 1 ms WUP-Excitation 的第一帧之后几乎放不下第二帧，所以缺省设置
  下每个传输机会只有一帧触发帧或一帧 Read。

### 6c. 触发帧里原来不起作用的字段

- Channel Indication：接入点写入自己 2.4 GHz 主 20 MHz 信道的编号（§39.3.2.1）。本仿真器的 2.4 GHz
  链路只有一个信道、没有编号，取 6（model）。Active Tx 标签在该信道上作答，信道指示为 14、15 时不作答
  （§39.4）。
- UL 频移：接入点总是指示 0（§39.3.2.2 允许 +5、−5、0 MHz，接入点的选择）；250 kb/s 的标签按它
  偏移——为 0 时与不偏移相同。
- 扰码种子编号：接入点总是写 0，对应 SCRAMBLER_INITIAL_VALUE 0x5C（表 39-1）。本引擎不建模比特，
  扰码本身不计算。
- 三个字段都不是场景参数，所以不存在「允许而不起作用」的配置；字段视图显示它们的值。

### 6d. 注释里的条款

- CTS-to-self 的出处改为 §9.2.5.2 / §10.3.2.15（原来误引 §10.23.2.8）。

## 7. 2.4 GHz

- 短时隙（§10.3.2.16，§11.1.3.2；表 18-5、表 19-25）：基本服务集里每一台设备都支持短时隙时用 9 µs，
  否则用 20 µs。节点字段 `shortSlot`（dot11ShortSlotTimeOptionImplemented/Activated）；缺省 802.11g
  （ERP）不支持（表 18-4 的 MIB 缺省 false），HE/EHT/UHR 支持（表 19-24「implementation dependent」，
  本仿真器的取值）。AMP 标签不是基本服务集的 ERP/HT 站点，不参与。`engine/phy.ts#withLongSlot` 让
  DIFS、AckTimeout、EIFS 随时隙一起变。`shortSlot` 贴在不在 2.4 GHz 链路上的节点上会被 schema 拒绝。
- 2.4 GHz 的 EIFS（最低必选速率）：属于并行的 W6 工作流，本工作流不改。
- 256-QAM 2/3 对只支持 20 MHz 的设备可选：语料只在 TGbn 规范框架里找到（Motion #216，UHR）。本引擎让
  每台 UHR 设备都支持它——「可选」允许这样做，所以没有改动。

## 8. 没能核实或留给别的工作流的

- §39.4 说单站反向散射的第一个时隙在「承载征求帧的 AMP PPDU 最后一个符号结束之后一个 AMP SIFS」开始；
  单站的应答却必须落在同一个 PPDU 的 BST-Excitation 之内。本引擎沿用规范框架 PM-75 的 T1 = 16 µs
  （从 AMP-Data 结束起算），两者怎样统一草案没有说清。
- 读写器两帧之间的 16 µs（T2）仍取自文稿 11-26/0120r0。
- AMP RFID 帧（11-26/1520r3）与 AMP Response 帧格式（11-25/1678r2）在语料里是 PDT/提案，采纳状态以
  动议 #239 与 FM-25 为准；触发帧与 AMP Response 的字段宽度仍是「model」。
- Channel Indication 的编号 6 是本仿真器的取值。
