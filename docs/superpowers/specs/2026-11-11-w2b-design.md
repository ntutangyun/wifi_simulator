# W2b：改课时发现的 UWB 核心偏差（2026-11-11）

工作计划 `docs/superpowers/plans/2026-11-10-uwb-standard-alignment.md` 的 W2b 表，除「一对多窄带 POLL 长度」（另一个工作流）之外的七项。审计表 `docs/uwb-standard-audit.md` 新增 #25–#31。
硬规则照旧：只用 IEEE Std 802.15.4-2024 定义的帧、信息单元与规则；每一项都对照语料库原文（`ieee_standards/text/802154-2024.json`）核过。

## 1. 改了什么，依据哪一条

| # | 内容 | 标准 | 以前 | 现在 |
| --- | --- | --- | --- | --- |
| 1 | 应答方的时隙与角色 | §10.32.9.8：SIU = 1 时 RDM IE「allocate time slots and assign the ranging roles」；「Upon reception of the RCM, a controlee knows whether it is selected to participate」 | 应答方的时隙取自场景里的锚点顺序；没持有控制消息的锚点仍按时间表在 Final 与报告时隙打开接收机、写超时 | 时间调度的 Poll 为每个应答方带一个 RDM 元素（角色 = 响应方、Ranging Slot Index = 它的应答时隙，`PollOpts.rdmSlots` → `UwbInfo.rdm`）；应答方从自己的元素读出它在轮里的位置（`HeldRcm.responder`），据此发 Response、延后回复、报告、MMRCM，固定回复时间也按它取 FRTi。没有持有有效 RCM 的应答方不作答，第 0 个时隙之后不开接收机（`onSlot`）。发起方就是控制器，它自己写的时间表，不需要「收到」什么；辅助信息与 SP3 的 SRRR 在 W2 已按收到的信息单元行事 |
| 2 | 块由整数个轮组成 | §10.32.2「Each ranging block consists of a whole number of ranging rounds」；§10.32.3.3 轮数 = 块长 ÷ 轮长 | 块内轮数向下取整，余下的时间不用（200 ms 块装 12 个 16 ms 轮，余 8 ms） | schema 要求块长是时隙长的整数倍；轮长取「不少于本轮所需、又能整除块内时隙数」的最小时隙数，多出的时隙空闲（`uwb/phy.ts#uwbWholeRoundSlots`，`roundPlan`、schema、编辑器共用）。轮可以比它的交互长（§10.32.2 只要求「sufficient duration」），轮长是控制器上层的选择（ARC 的 Ranging Round Duration），取最小值是本仿真器的取法。编辑器在时隙或块长改动后把块长移到最近的整数倍（`uwbSessionRepair`） |
| 3 | 300 RSTU 最短时隙 | 标准没有；§10.32.2 只要求时隙能发送至少一帧；表 12-1 aTurnaroundTime = 12 个符号周期，§16.1 规定 HRP 的 MAC 定时以前导符号 Tpsym 计；§11.2.3、§16.4.8 | schema `slotRstu ≥ 300`，编辑器按 300 截断 | 去掉；时隙 ≥ 最长帧 + 200 ns 飞行余量（本仿真器的取值）+ aTurnaroundTime（12 × 508 码片 = 12 212 ns，`UWB_TURNAROUND_NS`）。编辑器的下限改为这条规则算出的值（`uwbSlotFloorRstu`）。MMS 时隙仍按草案的 300 RSTU 倍数 |
| 4 | DS-TWR 回报给发起方的时间 | 嵌入：§10.32.5 图 10-238，Response = `{Ranging, RRMC IE and RRTI IE}`，报告 `{RMI IE including roundtrip time}`；延后：§10.29.6.6 与图 10-206（「The subsequent reporting of the ranging result to the initiating end, using the RMI IE, depends on the value of the TOF Request field」），一对多见图 10-237、10-239 | Response 不带 RRTI（14 字节）；报告一个 RMI 带 treply1 与 tround2（23 字节），两种形态一样 | 嵌入：Response 带 RRTI（Treply1，21 字节），报告只带 Tround2（19 字节）。延后：Response 不带回复时间（Deferred Mode，§10.32.9.1）；锚点从发起方的延后数据帧算出距离后，报告用 RMI 的 TOF 字段（RCTU 整数，§10.29.8.4、§10.29.1.4）把它发回（19 字节），发起方直接采用。SP3 双边（总是延后形态）同样报告 TOF，由发起方在 SRRR 里置 RTOF 请求（§10.32.9.9） |
| 5 | SS-TWR 的 Response 是否带 RRMC | §10.32.4 图 10-235：一对多时应答带 RRTI 与 RRMC (1)（「to convey the RRMC IE with Ranging Control Information field set to one」）；图 10-204 是一对一，应答只带 RRTI | 带 RRMC 与 RRTI | **核实，未改**：本仿真器的会话都是一对多（ARC Multi-node Mode 1），照图 10-235。`uwb-sstwr` 的 ② 行补注了出处 |
| 6 | 「序列关闭」 | 表 16-1：不带 STS 的分组是配置 0；表 10-165：ARC 的 STS Packet Config 0 =「No STS field included in the PPDU」 | 只关掉接收端的判断，帧仍按配置 1 计长度 | `stsOff` 时每一帧按配置 0 发送（`frames.ts#withoutSts`，`device.send`）：SHR + PHR + PSDU，短 33 792 码片；`UwbInfo.sp = 0`；ARC 写 STS Packet Config 0；帧检查器画出无 STS 的分组。schema 拒绝 `stsOff` 与 `sp3` 同开（SP3 分组只有 SHR + STS），拒绝 `stsOff` 用于 MMS（未实现） |
| 7 | RMNR 能否发出 | §10.34.1、图 10-270：持有 RCM、没收到启动消息的应答方可以在自己的时隙发 RMNR | 机制照标准，但课程里没有一个场景能让它发出，`uwb-rcm-validity` 变体里的 `rmnr` 开关不起作用（permitted-but-inert） | 引擎不变（组首两条消息合并是标准允许的，§10.32.2）。`uwb-rcm-validity` 的第三个场景加一台在后台备份的 Wi-Fi 笔记本（6 GHz 71 号信道，会话移到与之重叠的 UWB 5 号信道）：它偶尔淹没组里后几轮的启动消息，持有控制消息的锚点于是发出 RMNR（前 450 ms 里 3 轮、9 帧）；墙后的锚点从未收到控制消息，一帧也不发 |

## 2. 未实现

- 控制器不是发起方的会话（图 10-222 的一般情形，控制消息由别的设备发出）：本仿真器的控制器总是标签。
- 同一轮里把控制消息与启动消息分成两帧（图 10-270）：本仿真器总在组首合并（标准允许）。
- MMS（4ab 草案）轮的整数轮规则：MMS 的测距周期有草案自己的时隙布局，由 W5 处理；现在的 MMS 场景块内仍有余数（审计 #26 已注明）。
- DL-TDoA、UL-TDoA、多对多的应答方仍按场景顺序取时隙：这几种模式分别归 W4、W3。（多对多已在 W3 改正：设备从控制器 RCM 的 RDM 读角色与时隙，见 `2026-11-11-w3-design.md`。）
- `stsOff` 用于 MMS。

## 3. 本仿真器的取值与取法（标准留给实现的）

- 轮长取能整除块的最小时隙数（标准只要求整数个轮、轮够长）。
- 200 ns 的飞行余量。
- 设备本身的收发转换时间取 0（容量规则按 aTurnaroundTime 留出余量）。
- 延后 DS 的发起方请求的是 TOF（图 10-206 的做法），而不是另一种可能的「Treply1 与 Tround2」。

## 4. 核查不了的

- aTurnaroundTime 的 12 个符号按前导符号计：依据 §16.1 的一句「For the HRP UWB PHY, where MAC timing is specified in symbols, the duration of a preamble symbol (Tpsym) is used」；码长 127（L = 4）下 Tpsym = 508 码片，其他码长另算。
- RMI 的 TOF 字段按 RCTU 计（§10.29.8.4「The units of time are specified in 10.29.1.4」），取整方式（四舍五入）标准没有说。

## 5. 动到的数与 fixture

- DS 嵌入式 Response 21 字节；DS 报告 19 字节；延后 DS 手机的距离是锚点 TOF 取整后的值（`uwb-reply-time` 的工作台上 5.001420 m，锚点 4.999075 m）。
- 轮长：许多轮被拉长到能整除 100 个时隙的长度（3→4、7/8/9→10、11/17→20），时隙数随之变化的课：blocks、slot-budget、reply-time、contention、receipt（位图 41→68 位、MMRCM 24→27 字节）、m2m、sp3（课里的「时隙」改为「交互占用的时隙」）。
- 最短时隙：四个锚点的 DS 轮 306 RSTU（以前 292，另有 300 的下限）。
- 墙后／远处没有控制消息的锚点不再在 Final 时隙等待：capstone 的超时 40 → 33，coexist 饱和场景的干扰丢失 200 → 100。
- `tests/fixtures/lesson-hashes.json` 与 `uwb-record-hashes.json`：所有双向测距课程场景的条目重新生成（48 + 48 条），原因是上面 1、2、4 三项改变了帧的内容、长度与轮长；MMS 场景的条目没有变。
