# 多消息收妥确认：发送方怎么知道谁听见了

2026-10-02。已发布标准 §10.36 与它的 RMMRC IE（§10.36.2.1），加上 ARC IE 的
MMRCR 请求位（§10.32.9.1 bit 15）。`docs/uwb-modellable-backlog.md` 的切片 3b。

## 1. 为什么只做 §10.36，不连 §10.35 一起做

原来的排期把 §10.35 与 §10.36 放在一刀。**读通机理之后它们不该在一刀里**，
而理由不是切片大小，是其中一半需要动一个别的模式也共用的结构。

§10.35 的 RAICT IE 有两种用法，由 Request 位区分：

- **Request = 0**：报出当前这一帧的序号、这条消息还剩几帧、以及消息类型。
  这一半建得出来。
- **Request = 1**：**向控制器请求下一次交互排几个时隙**（Frames Remaining 这时
  装的是请求的时隙数）。这会是本引擎第一处**由设备发起的排程请求**。

而问题在第二半：本引擎的 `RoundPlan` 在 `UwbNetwork` 的构造函数里**一次算定**，
整个会话共用。要让一个请求真的改变后续的排程，就得把轮的排布变成每块重算一次——
那是一个 DL-TDoA、MMS、多对多全都共用的结构。

**那不该夹在一刀的后半截里做。** 所以 §10.35 单独一刀，而它真正的题目不是
「加一个信息单元」，是「排程能不能被请求改变」。本刀只做 §10.36。

## 2. §10.36 买到的那件事，正好是切片 2 留下的问题

切片 2 的结论里有一句读者一定会追问的：**参与者 N−1 发出全轮最长的帧，却算出零条
距离**，而且每一对距离只有**排在前面**的那一个算得出来。

于是一个参与者知道「我算出了到谁的距离」，却**不知道谁听见了我**。

§10.36 就是这个的答案。标准的话：响应方可以用一帧 MMRCM（multiple message
receipt confirmation message）确认它收到了**来自同一个发起方的多条消息**，或者
**来自多个发起方的消息**。而标准为它画的那张图（Figure 10-272）标题就写着
**Many-to-Many Messages**：A1…AN 各发若干条给 B1…BM，发完之后 B1…BM 用
多播或多节点消息把收妥情况回给各个发起方。

**所以这一节接在多对多之后最顺，不是巧合，是标准自己这么画的。**

## 3. 建什么

### 3.1 请求：ARC IE 的 MMRCR 位

控制器在 RCM 的 ARC IE 里置 **MMRCR**（bit 15）就是在请求收方回确认。
本引擎的 ARC IE 已经建了 Content Control 里的 RCM Validity Rounds（bit 9–14），
MMRCR 是同一个字里的下一位，所以这一位**不增加帧长**——它本来就在那两个字节里。

**这一点要在课里说清：请求一次收妥确认，上行方向一个字节都不花。**
花钱的是回答。

### 3.2 回答：MMRCM 与 RMMRC IE

RMMRC IE 的内容字段：

| 字段 | 宽度 | 含义 |
| --- | --- | --- |
| Address Present | 1 bit | MMRC 列表的每个条目里有没有地址字段 |
| Address Size | 1 bit | 有地址时它多长 |
| 保留 | 6 bit | |
| MMRC List Length | 1 字节 | 列表里有几个条目 |
| MMRC List | 变长 | 每个条目：（可选）地址 + 一张收妥位图 |

**一个条目对应一个发起方**，位图说的是「你发来的那几条，我收到了哪几条」。

### 3.3 位图覆盖的是哪几条消息

标准说的是「多条消息」，没有替本引擎指定是哪几条。本仿真器取
**当前 RCM 有效期窗口里该发起方发出的那几条开场消息**——也就是切片 3 刚建的那个
窗口：R = 4 时是一条控制消息加三条启动消息，位图四位。

这是一个**模型决定**（标 `model`），理由有两条：窗口是引擎里现成的、两端都已经同意
的那个边界（`uwb/session.ts#blockCarriesRcm`），不需要再商量一个新的；而且它让
切片 3 与本刀直接咬合——一张位图正好回答「我这四块的开场，你收到了几块」。

于是帧长：`MHR 9 + IE 头 2 + 控制 1 + 列表长 1 + 每个发起方（地址 2 + 位图 ⌈R/8⌉）+ FCS 2`。
R ≤ 8 时位图一个字节，所以一个发起方 3 字节，**N 个发起方的 MMRCM 是 15 + 3N 字节**。
上限照老规矩**算出来**，不写字面量。

## 4. 它让谁知道了什么

| | 切片 2 之后 | 本刀之后 |
| --- | --- | --- |
| 参与者 i 到 j（i<j）的距离 | i 知道 | i 知道 |
| 谁听见了参与者 i | **没人告诉它** | i 从每个人的位图里读出来 |
| 一个窗口里哪一块的开场丢了 | 只有超时，分不清 | 位图里那一位是 0 |

**第三行是本刀与切片 3 咬合的地方**：RMNR 说的是「我没收到本轮的启动消息」，
是逐轮的、由响应方主动发的；收妥位图说的是「你那四块的开场我收到了哪几块」，
是整窗口的、由控制器请求的。两者回答的是同一件事的不同粒度，而课程要把这一点
摆出来——**不然读者会以为它们是一回事。**

## 5. 验收：跑完整轮，读它的输出

1. **位图对得上真实的丢失。** 多对多一轮加一面墙，使某几对听不见：读 MMRCM 的位图，
   它标出的 0 位与 `RX_OK` 的缺失**逐位对上**。这是本刀的验收——位图不是记录的复述，
   它必须是从接收端自己的经历里来的。
2. **请求不花空口时间。** MMRCR 置位前后，RCM 的字节数**完全相同**（它在既有的
   Content Control 两字节里）。
3. **回答的帧长按 §3.3 的式子长**：N 个发起方 15 + 3N 字节，对 N = 1、3、6 各验一次。
4. **测距结果不变。** 打开 MMRCR 之后 `UWB_RANGE` 逐字段与关闭时相同——
   收妥确认是一条额外的消息，不是测量的一部分。
5. **不请求就没有回答。** MMRCR 为 0 时一条 MMRCM 都不发。
6. **既有场景逐字节不变**，两份 fixture 零 diff。

## 6. 明确不做

- **§10.35 整节**，理由见 §1：它真正的题目是「排程能不能被请求改变」，
  那要动一个所有模式共用的结构，单独一刀。
- **地址压缩**：Address Size 那一位建成固定的短地址（2 字节），
  不建长地址那一种。标 `model`，并说明标准允许两种。
- **多播／多节点下发**：标准允许 MMRCM 用多播或多节点消息一次回给多个发起方。
  本引擎不建多播的收发，**范围决定**。

  ### 6.1 更正（2026-10-02，Task 3 实现时发现）

  本条原文写的是「本引擎**每个发起方一帧**」。**那对双向轮是对的，对多对多是不可能的。**

  时隙是**每个响应方**一个（§3.3 已更正过的那个数），所以多对多里 N 个时隙装不下
  N(N−1) 帧。多对多里一个参与者发**一帧，里面 N−1 个条目**——而那恰恰是 §3.2
  那张列表、以及 `uwbMmrcmBytes(initiators, …)` 的第一个参数存在的全部理由。

  **这是同一个错在另一层:** `2a93944` 刚把「每个发起方一个时隙」改成「每个响应方
  一个时隙」，而这句散文里的「每个发起方一帧」是同一笔糊账的另一半，**在代码改对
  之后继续活在文字里**。§10.36 有两个计数，而把它们写进同一句话就会错一次：

  | 数什么 | 一个什么 |
  | --- | --- |
  | IE 的列表条目 | 每个**发起方**一个（一个响应方可能听到好几个） |
  | 时隙 | 每个**响应方**一个（各自发自己那一帧） |
  | **帧** | **每个响应方一帧**，里面装它听到的那些发起方 |

  双向轮里一个响应方只听到一个发起方（那个标签），所以它那一帧只有一个条目——
  于是「每个发起方一帧」在双向轮里看起来是对的。**多对多才把它拆穿。**
- **加密与认证**：照旧，本仿真器没有一处密码学。
