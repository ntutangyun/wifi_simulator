# 测距辅助信息：一条消息装不进一帧的时候

2026-10-02。已发布标准 §10.35 与它的 RAICT IE（§10.35.2.1）。
`docs/uwb-modellable-backlog.md` 的切片 3c。

## 1. 我上一次写这一节的题目，写窄了

切片 3b 的规格里我写着：§10.35 真正的题目是「排程能不能被请求改变」，
而那要动 `RoundPlan` 这个所有模式共用的结构，所以单独一刀。

**查完正文，那只是它的一半，而且是较小的那一半。**

§10.35.1 与 §10.35.2.1 给的是两件事，由 RAICT IE 的 **Request** 位分开：

- **Request = 0**：报出当前这一帧的序号、这条消息还剩几帧、以及消息类型。
  正文把这一半的用途说得很直白：**把信息分装在多条 MAC 消息里，跨一轮之内的多个
  测距时隙发出去，并据此管理重传。** 这一半**不需要动任何共用结构**。
- **Request = 1**：向控制器请求下一次交互排几个时隙（Frames Remaining 这时装的是
  请求的时隙数）。正文还多给了一个条件：**只有当发起方不是控制器时**，
  这一位才有意义——它是控制者之外的设备向控制者要东西。

**所以这一刀做 Request = 0，排程请求是切片 3d。** 分界线不是工作量，
是其中一半要让轮的排布每块重算一次，而那是 DL-TDoA、MMS、多对多全都共用的结构。

## 2. 两个角色名在这一节里换了意思

正文为辅助信息交换单独定义了两个词，而它们**与测距里的同名词不是一回事**：

| 词 | 测距里 | §10.35 的辅助信息交换里 |
| --- | --- | --- |
| 发起方（initiator） | 开启一次测距的那一端 | **发出辅助信息的那一端** |
| 响应方（responder） | 作答的那一端 | **接收辅助信息的那一端** |

于是一台在测距里作答的设备，在辅助信息交换里可以是发起方。**这件事要写进课**，
因为本引擎的 `slotAction` 是按测距角色排的，而这一刀要在同一套时隙上跑一个角色相反
的交换——读者看到一台「响应方」在发消息，会以为是 bug。

## 3. 窗口是切片 3 已经建好的那个

§10.35.1 说：这个交换发生在当前这一轮以及 RCM 之后的若干轮里，
而**受这条 RCM 管的轮数就是 ARC IE 的 Ranging Validity Rounds 字段**（§10.32.9.1）。

**那正是切片 3 建的那个窗口**，引擎里是 `uwb/session.ts#blockCarriesRcm` 与
`UwbSessionCfg.rcmValidityRounds`。所以这一刀不需要发明一个新的边界，
它用的是两端早就同意的那一个——与切片 3b 的收妥位图用的是同一个窗口，
而这是第三处用到它的地方，值得在课里点出来。

正文还说这个交换可以是**排程式的，也可以是竞争式的**。引擎两种都有
（`UwbSessionCfg.schedule` 的 `'time'` 与 `'contention'`），所以这一刀两种都要能跑，
**而且竞争式那一种必须真的有效果**——切片 3 的教训是 `contention` + `rmnr`
被允许却可证明地什么也不做，而那正是一个特性看起来做完了的方式。

## 4. 建什么

### 4.1 RAICT IE 的字节数是变长的，而且变在两个存在位上

内容字段（§10.35.2.1，Figure 10-271）：

| 字段 | 宽度 | 含义 |
| --- | --- | --- |
| Request | 1 bit | 这个单元是不是在请求时隙（本刀恒为 0） |
| Ranging Or Ancillary Message Number Present | 1 bit | 后面那个消息号字段在不在 |
| 保留 | 6 bit | |
| Ranging Or Ancillary Message Number | 0 或 1 字节 | 消息号 |
| Frames Remaining | 0 或 1 字节 | 这条消息还剩几帧 |

所以内容是 **1 到 3 字节**，而它长成几字节由那个存在位决定。
`raictIeBytes(numberPresent, framesRemainingPresent)` **算出来**，不写字面量。
这是本引擎第一个**由存在位决定长度**的信息单元，值得单独测：
两个存在位的四种组合各一条。

### 4.2 分段：一条消息跨多个时隙

本刀建一条「辅助信息消息」，它比一帧装得下的多，于是分装在同一轮里连续的几个时隙上。
每一帧带一个 RAICT IE，Frames Remaining 从 N−1 数到 0，接收端按它判断收齐了没有。

**模型决定（标 `model`）**：一条消息分几帧，由场景配置给出
（`UwbSessionCfg.ancillaryFrames`），而不是由一个真实的上层应用算出来——
本引擎没有一处 MAC 原语，也没有上层。这条要写进 `limits`，
照 `rcmValidityRounds` 已有的那条理由写。

### 4.3 重传：收不齐的那一帧

正文把管理重传列为这个单元的用途之一。本引擎能建出来的那一半是：
**接收端按 Frames Remaining 发现缺了哪一帧**，而不是由超时推测。
这与切片 3 的 RMNR、切片 3b 的收妥位图构成第三种粒度，而三者的区别必须在课里摆开：

| | 谁发 | 什么粒度 | 回答的问题 |
| --- | --- | --- | --- |
| RMNR（§10.34） | 响应方主动 | 逐轮 | 本轮的启动消息我没收到 |
| 收妥位图（§10.36） | 控制器请求 | 整个有效期窗口 | 你那几块的开场我收到了哪几块 |
| **Frames Remaining（§10.35）** | **发送端自己带着** | **一条消息之内** | **这条消息还有几帧没来** |

**第三行是新的那一行**，而它与前两行的差别是：它不是一次回报，
是**发送端在每一帧里都说一遍还剩几帧**，所以接收端不需要等任何东西就知道缺了哪一帧。
三者放在一起，读者才看得出「丢了」这件事在标准里有三个不同的层次。

## 5. 验收：跑完整轮，读它的输出

1. **分段真的跨时隙。** 一条 N 帧的辅助消息，读记录：N 帧各占一个时隙，
   Frames Remaining 从 N−1 单调数到 0。
2. **存在位真的改变帧长。** 四种组合各测一次，帧长按 §4.1 的式子长，
   并且**全部由 `raictIeBytes` 算出来**。
3. **缺帧是被发现的，不是被超时猜出来的。** 加一面墙让中间某一帧收不到：
   接收端在**后一帧到达时**就知道缺了哪一号，而不是等整条消息超时。
   这是本刀的验收。
4. **竞争式那一种有效果。** `schedule: 'contention'` 下跑同一条消息，
   记录与排程式**不同**（时隙不再是预先指定的那几个）。
   不许出现一个被允许却可证明无效果的组合。
5. **测距结果不变。** 打开辅助信息交换之后 `UWB_RANGE` 逐字段与关闭时相同。
6. **不配置就什么也不发。** 缺省关，一帧 RAICT 都不发。
7. **既有场景逐字节不变**，两份 fixture 零 diff。

## 6. 明确不做

- **Request = 1 的排程请求**：切片 3d。理由见 §1——`RoundPlan` 在 `UwbNetwork` 的
  构造函数里一次算定、整个会话共用，要让一个请求改变后续排程就得把轮的排布变成
  每块重算一次，而那是所有模式共用的结构。**这不是举证不足，机理已经读通**
  （Request 位、Frames Remaining 的第二种含义、以及「发起方不是控制器时」这个条件）。
- **消息类型字段的取值表**：正文说 Request = 0 时这个单元还报消息类型。
  本引擎只建一种辅助消息，所以类型建成一个常量，不建取值表。标 `model`。
- **MAC 原语与上层**：照旧，本仿真器一条 MAC 原语都没有，
  所以「上层用这些字段来管重传」这件事只建到 MAC 能看见的那一半。
- **加密与认证**：照旧，没有一处密码学。
