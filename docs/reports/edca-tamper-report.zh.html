EDCA 篡改驱动对手游时延的影响与检测

七种违反 IEEE 802.11 EDCA 参数的终端"作弊"方式：原理、检测方法、AP 能否单独发现，以及在四个手游场景中对作弊者与合规终端 ping 的仿真影响。数据来自本仓库的确定性仿真引擎（µs 级 DCF/EDCA，含真实往返的云服务器）。生成时间 2026-09-09。

1 · 主要结论

  1. 轻载家庭里作弊没有任何收益。三人开黑场景空口只用了 22%，七种作弊下作弊者的平均 ping 与基线 28.8 ms 的最大偏差只有 0.0 ms：没有竞争可赢，WAN 的 25 ms 决定一切。
  2. 重负载下，抢竞争的作弊立竿见影。两台笔记本饱和上传把空口占满（102%，每秒 183 次碰撞事件），基线 ping 涨到 66.0 ms。作弊者收益最大的是"优先级抬升"：66.0 ms → 46.8 ms（-29%；3/3 个种子同向，各种子 61.3→47.2、71.9→50.2、65.6→43.2），合规玩家的 ping 也随之下降（75.1 ms → 65.6 ms；2/3 个种子同向）。合规玩家为何也受益（且并非每个种子都如此），本报告的计数器没有分离出机制——他们自己的碰撞与重传次数几乎不变（见第 5 节），只能说重负载下一个抢先的终端并没有把玩家挤得更惨。其次是 CW 坍缩（50.3 ms）、贪婪（50.3 ms）。
  3. 合规玩家付出的最大代价来自"NAV 膨胀"（满屋子人 + 作弊者同时云备份）。他们的平均游戏 ping 从 32.9 ms 升到 35.6 ms（+8%），P95 41 → 49 ms；同一配置下作弊者自己 32.2 ms → 32.6 ms。能解码作弊者帧的终端每次都把 NAV 多设 3 ms，在作弊者早已沉默时仍不敢竞争。（3/3 个种子同向：33.8→34.1、32.5→37.6、32.4→35.1）
  4. TXOP 霸占对只打游戏的作弊者无用；NAV 膨胀有效与否取决于邻居能否解码它的帧。游戏包 100 B、每 16.7 ms 一个，没有可以霸占的突发：在只打游戏的三个场景里，TXOP 霸占下作弊者的平均 ping 与基线的偏差不超过 0.0 ms（轨迹完全相同）。NAV 膨胀则不同：重负载场景 8 s 里作弊者发出 510 个数据帧，其他终端合计解码 689 次（一帧可被多台终端解码）、设置了 688 次比实际需要长 3 ms 的 NAV——能解码它的邻居每 16.7 ms 就被压住 3 ms。结果作弊者 66.0 ms → 59.9 ms，合规玩家 75.1 ms → 64.4 ms：被压住的主要是两台饱和上传的笔记本，所有玩家都因此受益。这一效果取决于谁能解码作弊者的帧：本引擎按每个 MCS 的 SINR 门限判定解码，与帧长无关，作弊者到 AP 的距离决定它用的 MCS，邻居能否解码常常只差零点几 dB——位置一变就可能一帧都解不出来。作弊者自己也在云备份时，它的 1500 B A-MPDU 超过 RTS 门限，每个突发都以 24 Mb/s 的 RTS 开头——RTS 的 Duration 同样被膨胀，而且所有邻居都能解码它：该场景 8 s 里 1864 次 NAV 设置来自作弊者的 RTS，1685 次来自其数据帧。TXOP 霸占让合规玩家 32.9 ms → 33.9 ms，NAV 膨胀让合规玩家 32.9 ms → 35.6 ms、其他终端 29.5 ms → 30.2 ms，而作弊者自己的 ping 分别为 33.6 ms 与 32.6 ms（基线 32.2 ms）。
  5. 满屋子 + 作弊者云备份：平均与尾部都没有收益。该场景空口 72%，作弊者基线平均 32.2 ms（P95 38，最大 73 ms），七种作弊的平均值都在 32.3–33.8 ms 之间。P95 在七种作弊下全都不低于基线（优先级抬升 48、AIFS 地板 42、CW 坍缩 41、不加倍 42、TXOP 霸占 44、NAV 膨胀 41、贪婪 40 ms），最接近的是"贪婪"：38 → 40 ms，最大 73 → 94 ms。作弊者自己的备份突发占着它的电台：每次 A-MPDU 突发的两三毫秒里，它的游戏包只能等自己发完，作弊改变不了自己的电台忙。
  6. 检测责任分工。优先级抬升、TXOP 霸占、NAV 膨胀和贪婪都留下 AP 单独可测的硬证据（TID、TXOP 时长、Duration 字段）；AIFS 地板与 CW 坍缩只在发送时刻分布上留痕，AP 的介质视角与作弊者不同，需要统计样本，合规终端的旁证有帮助但不是必需；不加倍要靠重传帧前的等待，而碰撞事件本身 AP 看不见，把碰撞归因到作弊者需要合规终端报告的重传率。详见第 3 节。

{"aifsn":1}
所有类别 AIFSN = 1（AIFS 25 µs，正常 VO 34 / BE 43 / BK 79 µs）

介质空闲后只等 SIFS + 1 个时隙就开始倒数或发送，比任何合规终端都早一到六个时隙进入竞争。

 测量该终端每次发送前的"空闲间隔"：从 AP 看到的介质空闲起点到该终端前导到达。作弊者仍会抽退避，所以间隔并非常数，但其下限是 25 µs（SIFS + 1 时隙），而合规终端的下限是 AIFS[AC]（VO 34、BE 43 µs）：看分布的最小值与其在所有类别上的一致性。 足够（统计）

不加倍
{"noDoubling":true}
CWmax 钉在 CWmin：碰撞或丢 ACK 后窗口不增长

§10.3.3（DCF）与 §10.23.2.2（EDCA）要求每次失败后 CW 取下一个 2ⁿ−1；作弊者始终用 CWmin 重发，在拥塞时反复抢占。

 Retry=1 的重传帧前的空闲等待没有随重传次数增长；第 n 次重传的等待分布与首发完全相同。 需协助

NAV 膨胀
{"navInflateUs":3000}
每个帧的 Duration 字段 +3 ms

让所有听到该帧的终端把 NAV 设得比交换实际需要的长 3 ms，在作弊者沉默时仍不敢竞争。

 Duration 字段 vs 实际所需：单次保护下应为 SIFS + ACK/BA，多重保护下最多到该 AC 的 TXOP 剩余时间——+3 ms 超过了 BE 的 2.528 ms 限值，AP 能直接判定；小于 TXOP 剩余量的膨胀则与合法的多重保护无法区分。合规终端也能发现：NAV 期间介质长时间空闲。 足够

AP 一定能解码作弊者发给它的帧，Duration 语义是确定的。作弊效果取决于谁能解码作弊者的帧：解不出帧就读不到 Duration（各场景的解码计数见第 1 节），而 AP 是唯一确定能解码的接收方。

6 · 方法与局限

  • 引擎。事件驱动、整数纳秒时钟；DCF/EDCA（Table 9-194 参数）、A-MPDU/BlockAck、TXOP、RTS/CTS、NAV、OFDMA、MLO；传播为对数距离 + 墙体损耗，前导检测 −82 dBm、能量检测 −62 dBm，同时起始按信号强度判定捕获。篡改驱动通过 NodeCfg.tamper 覆盖该终端的 EDCA 参数（effectiveParams），并在其发出的 Duration 字段上加膨胀量。
  • 作弊者只有一个。报告回答"一台越权终端能得到什么、让别人付出什么"；多台作弊者互相竞争是另一个问题。
  • NAV 膨胀的效果取决于解码，而本引擎的解码模型偏保守。引擎按每个 MCS 的 SINR 门限判定一帧能否解码，解不出就不读 Duration（只得到 EIFS）；数据帧的 MCS 由作弊者到 AP 的链路决定，邻居能否解码常在零点几 dB 之间，因此同一作弊在不同位置的效果可以从"完全无效"到"压住全屋"。第 1 节给出了本次运行的解码与 NAV 计数。真实的 Wi-Fi 6/7 终端即使解不出载荷，也会按 HE/EHT 前导中的 TXOP_DURATION 更新 NAV（IEEE 802.11-2024 §26.2.4），本引擎未建模这一点，所以对"解不出就骗不到"的结论应打折扣。
  • 样本量与离群值。ping 每秒 4 次，单个 3 s 运行只有 11 个样本，一次 300 ms 的异常值就能把均值抬高 25 ms；因此改为 3 个种子 × 8 s 并合并样本。即便如此，一个种子里的一次长时延仍能左右合并均值，所以第 3 节每个变化都标注了"n/3 种子同向"（悬停可见各种子的值），第 1 节的结论只采用所有种子同向的变化；P95 与最大值是单点统计，解读时注意。
  • 本实验暴露并修复的两个引擎缺陷。（1）AP 发完一个下行 MU PPDU、收齐所有 BlockAck 后，原引擎还要再等 45 µs 的应答超时才结算这次交换、再等 SIFS 才续发——TXOP 持有者每次 MU 后空等 61 µs，比任何类别的 AIFS 都长，任何终端都可以合法地插进来。现在收齐最后一个 BlockAck 就立即结算。（2）被插入一个必须应答的帧（作弊者的 RTS）时，原引擎同时保留"续发"与"应答"两个定时器，第二个在自己发送中途触发 startTx while transmitting；现在收到必须应答的帧会取消续发并结束 TXOP，续发定时器触发时若 CCA 忙也会放弃。按 §10.3.2.9，被 RTS 点名的终端只要 NAV 空闲就应答 CTS，持有者自己的帧不设置自己的 NAV，所以应答是合规的；而在单次保护下持有者的 TXNAV 在 BlockAck 结束时已经到期，放弃 TXOP 也合规。
